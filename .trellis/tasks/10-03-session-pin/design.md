# 会话置顶 —— 技术设计与决策记录

> 需求与验收标准在 `prd.md`。本文件只回答「怎么定、为什么这么定」，
> 每条决策都要求下一轮不必重新论证一遍。

## 一、数据形态：抄 `archive.json`，不发明第二套

`SessionPinStore`（`src/main/daemon/pin.js`）与 `SessionArchive` 同形态：
配置目录的 `pins.json`、`{ 绝对路径: 置顶时刻 }`、惰性加载、
损坏 / 缺失 / 结构不符一律当空索引、`临时文件 + rename` 原子落盘、状态没变就不落盘。

**为什么是独立索引而不是写进会话文件**：会话文件是 pi 的资产，往里面写东西必须经过
**活的** `SessionManager`（同一文件两个活写者会互相覆盖 entries —— 见 `session-host.js`
里 `renameSession` 的注释），而置顶是一条**纯展示偏好**，不值得为它承担那种耦合。
失败形态也更好：索引坏了最坏是丢置顶，会话本身不受影响。

**为什么不清理指向已消失会话的条目**（`archive.json` 也没清理）：
会话文件可能只是暂时不可达（同步目录还在拉、外置盘没挂），按「文件不在就删」清理
会把用户的选择悄悄抹掉。索引大小以「用户点过多少次置顶」为上限，不值得引入这个风险。

**键用 `resolve()` 后的绝对路径**（与归档同一套写法）：两个索引指向同一批会话文件，
键的规范化不能各写一套，否则「同一个会话」在两个索引里会是两条不同的键。

## 二、排序：置顶优先，**但只在自己那一组内部**

唯一改动点是 `groupSessions`（`app.js`）：任务区与自己那一组会话各自
`sortSessionsByPin`，**分区之间、空间组的先后、当前工作空间的组序（issue #73）一律不动**。

| 决策 | 理由 |
| --- | --- |
| **分区内置顶**，不做「全局置顶区」 | 侧栏是「任务 / 空间→会话」两层结构。全局置顶区要把行从它所属的工作空间里**抽走**，用户会问「它怎么在这儿」；而分区内置顶与 issue #73 的既有做法同构（那边也是「组内排序信号 + 形态」，没开新容器）。VS Code 的 pinned tab 是同一个隐喻：**排在原地最前，不搬家** |
| 置顶区内部仍按 `modifiedAt` 倒序 | 「置顶」的语义是「这条要一直在手边」，不是「我要给它们定序」。用置顶时刻排会让刚聊过的置顶会话藏在另一个置顶会话下面，与全站「最近动过的在上面」相冲 |
| **不加「置顶」分组标题** | 侧栏只有 264px，且已有一层「任务 / 空间」分组；再加一层标题会让「置顶」这个概念在任务区与每个空间组各出现一次，层级 2→3。位置（浮到最前）+ 形态（钉标记）已经满足 DESIGN §2.1 的第一顺位信号 |
| **不做拖拽排序** | 拖拽要新的持久化形态（有序数组）+ 拖拽交互 + 键盘可达性 + 与「折叠 / 过滤后顺序」的一致性，成本远超「一个功能一个 PR」；而且与「时间分组」这类候选正面打架。`pins.json` 的形态可以无损迁移到有序数组（缺失项回落到 `modifiedAt`），路留着 |
| **不加每个分区的置顶上限** | 调研建议「每分区 5 条」（= 任务区一屏），理由是「不封顶 = 功能退化」。**不采纳**：真正要防的失效形态是「钉住了却看不见」，而这一条已经由**折叠窗口规则**从结构上解决了（见下条，与置顶条数无关）；加上限只是给一个自限行为再加一条拒绝路径与一套计数语义（已归档的算不算、取消归档后超限怎么办）。将来若真出现「置顶多到没意义」的反馈再回来加 |

## 三、折叠窗口：置顶项**不参与**那 5 个名额

任务区默认只渲染 5 行（`TASKS_COLLAPSED_COUNT`）。若沿用「先切片、再置顶」，
会出现这个功能最典型的失效：**置顶了，但它还在「查看更多」后面**。

所以窗口规则改成 `taskListWindow(sessions, limit)`：**先取出全部置顶项占位，
剩下的名额才给非置顶项**（`limit` 因此是「非置顶项最多显示几个」）。
置顶超过 `limit` 时窗口会变长 —— 宁可多显示，也不能把用户钉住的那条藏起来。

## 四、入口：`⋯` 菜单，**不开第二个 hover 按钮**

⚠️ 这条与「外请 UI/UX 设计师的建议」**相反**，是本次唯一一处刻意偏离评审意见的地方，
理由如下（本项目规矩：判定「这是问题」之前先在代码里搜有没有决策记录）：

`app.css` 的 `.task-item-ops` 注释里记着一条 2026-09-16 的**刻意决定**：
「里面**只有一个「⋯」**：此前并排四个 20px 图标、gap 只有 2px，窄栏里挤成一簇、
看着像叠在一起 —— 动作全收进 `.task-op-menu`。」

设计师主张「钉 + ⋯ 两个按钮」，并给了量化预算（簇宽 42px、hover 期最多压住标题尾
约 1.5px）。评估后仍不采纳：

- 它推翻的正是那条决定本身（「动作全收进菜单」），而**置顶是低频动作**
  （一条会话钉一次），不像复制 / 发送那样值得常驻一个按钮
- 「压住标题尾 1.5px」这种量级**只有真跑起来看画面才能确认**，而本次会话的沙箱里
  Electron 起不来（见 `implement.md` 的「环境限制」）—— 拿不到视觉验证就去改一个
  已经被否过一次的布局形态，是把风险留给下一轮
- 主流做法本就一致：ChatGPT / Claude / Cherry Studio 的置顶都在会话的 `⋯`
  / 右键菜单里，菜单是**行级动作的可发现的家**（本仓库里它已经住着 导出 / 重命名 /
  归档 / 删除）

**采纳了设计师的另一半**（这部分是实打实的缺陷，与上面无关）：`⋯` 所在容器
`.task-item-ops` 用 `visibility: hidden` 隐藏 —— 那会把按钮**移出 Tab 序列**，
`:focus-within` 永远不可能触发，于是行内**所有**动作对键盘用户都是关闭的。
改为 `opacity` + `pointer-events`（详见 `docs/DESIGN.md` §7.9），空间组头的
`.space-group-actions` 同款问题一并修（两处 CSS 本来就写着「逐条对齐」）。

## 五、状态怎么表达（形态 / 位置 / 无障碍）

| 项 | 取值 | 依据 |
| --- | --- | --- |
| 钉标记 | `.task-pin-mark`，`IconPin` 12px，色 `--text-secondary` | 与分支标记（`.task-branch-mark`）**共用同一条规则**，都是「标题前缀的次级标记」，同档视觉重量；不借状态色（置顶不是状态，§2.4）；12px 用四根直线画（有弧度的图钉缩到 12 会糊） |
| 位置 | 标题前缀的**最左**（钉 → 未读点 → 转圈 → 分支 → 标题） | 置顶是跨未读 / 运行态都稳定的**结构属性**，固定在 x 最左 → 所有置顶行的钉在同一列，「位置」独立成为第一信号（§2.1） |
| hover | 钉标记**不隐藏** | hover 正是用户去看「这行是什么」的时刻，此时把状态抹掉等于状态在需要时消失 |
| 无障碍 | 菜单项文案随状态切换（「置顶」/「取消置顶」）；标记 `aria-hidden`（`Svg` 自带） | 状态由位置 + 形态 + 菜单文案三路独立可读（§7.6）；菜单项是普通按钮，Tab 可达（修完 §7.9 之后） |
| 反馈 | **不弹 toast** | toast 在本项目的语义是**后台异步结果**（任务完成 / 失败）。置顶的结果（行挪到最前 + 钉出现）就在同一屏、且可逆，用全局提示是重量级误配。**失败必须弹**（写盘失败时行不会动，不说就是「点了没反应」） |
| 排序后是否做位移动画 | **不做**（瞬时跳位） | §5.1 禁止过渡布局属性；FLIP 是另一件事，本轮不做 |

## 六、范围红线（本轮不动的地方）

- **命令面板（⌘K）的排序不动**：它是**检索排序**（精确→前缀→子串→模糊，同分动作优先），
  往里混「置顶优先」会让「输入几个字，最匹配的却不排第一」——为了一个组织功能破坏一个
  检索功能。将来要做，正确形态是**加分组**（空查询时在「最近会话」之前插一组「已置顶」），
  不是改排序
- **首页「最近会话」不动**：它的名字就是口径 —— 一个两周没动过的置顶会话出现在
  「最近」里就是在撒谎。要让首页也露置顶，另起一组，不改这一组的排序
- **归档 / 删除 / 导出 / 分叉的既有逻辑一行不改**：置顶作为独立索引天然与它们解耦
  （要验证的只是「不会互相破坏」，已写进用例）

1. 去掉 `compareSessionsByPin` 的置顶比较键（只留 `modifiedAt`）：

   × 置顶的排在最前，其余保持最近活动在前

   × 置顶会落盘，另一个实例（= 重启后的 daemon）能读回

   纯逻辑文件一行未红，恰好只打中「与磁盘有关」的那些。
