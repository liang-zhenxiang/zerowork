# 收口 DESIGN.md 的受控例外登记表

## 问题（Issue #35）

`docs/DESIGN.md` §5.1 明文禁止过渡布局属性（`width` / `height` 等），
要求破例必须**登记并编号**，并声明「**未登记的布局属性过渡一律不放行**」。

**但 `app.css` 引用的例外编号与登记表对不上。**

### 登记表里只有两条

| 编号 | 例外 |
| --- | --- |
| ④ | `flex-basis` 过渡 —— 左侧栏折叠、右侧栏补齐 |
| ⑤ | `height` 过渡 —— 轨道高度 |

### 而 `app.css` 引用了 ① ③ ④ ⑤

| 位置 | 引用 | 内容 |
| --- | --- | --- |
| `app.css:5190`、`:5211` | **受控例外 ③** | 预览面板的 **`width` 过渡**（停靠态调宽 ±10px 与全屏切换共用） |
| `app.css:2978` | ① | 伪元素拿不到文字内容，扫光以文字形状为裁剪源 |
| `app.css:4724` | ⑤ | `height` 过渡（轨道高度） |
| `app.css:983`、`:5104`、`:5142` | ④ | 侧栏折叠 / 右侧栏补齐 |

**①②③ 在代码里被当作已登记的例外引用，但登记表里不存在。**
其中 **③ 是一条 `width` 过渡** —— 按 §5.1 的措辞，它目前处于**未登记状态**。

## 为什么不能直接补表了事：编号体系有歧义

- `app.css:970` 把 `flex-basis` 称作「**第二条 width 受控例外**」
- `app.css:983` 又把侧栏折叠称作「受控例外 **④**」

**同一件事同时被叫做「第四条」和「第二条 width 例外」—— 两套编号并行存在。**

所以第一步不是补表，而是**先确定编号体系是什么**：
- **全局序号**（①②③④⑤…，按登记顺序）？
- 还是**按禁止项分组**（width 一组、height 一组，各自编号）？

## Requirements

- R1 **先厘清编号体系**，在 `DESIGN.md` 里把规则写清楚（包括「为什么这样编」）
- R2 按厘清后的体系，把 `app.css` 里**实际存在**的全部受控例外补进 §5 的登记表，
  每条写清理由（代码注释里多半已有，搬进文档即可）
- R3 若某条**不成立**（例如它其实不需要例外、或有合规写法），
  **改用合规写法**并在 PR 里说明 —— 不要为了凑表而硬登记
- R4 补完后**两边一一对应**：代码引用的编号在表里都能查到，表里的编号在代码里都有出处
- R5 **用测试钉住**：加一条检查，断言「`app.css` 里引用的例外编号都在 `DESIGN.md` 的表中」——
  防止以后又漂移

## Acceptance Criteria

- [ ] `DESIGN.md` 写明了编号体系与规则
- [ ] 代码引用的编号与登记表一一对应（可用 `rg '受控例外' src/renderer/src/app.css` 逐个核对）
- [ ] R3 对每一条都给出了判断（成立 / 不成立 / 改用合规写法）
- [ ] 新增检查能在编号漂移时失败（**反向验证**：临时改一个编号，检查必须红）
- [ ] `npm run lint:all` 全过
- [ ] **不改动实际视觉效果**（除非 R3 判定某条应当改）

## 约束

- **不动 `app.css` 的视觉值** —— 本任务收口的是**文档与编号**，
  除非 R3 判定某条例外本不该存在
- 不为了改样式而大规模重排 `src/renderer/src/`（`AGENTS.md` 红线 6）
- `docs/DESIGN.md` 是设计规范的事实来源，改它要同步检查引用它的注释
  （`rg 'docs/DESIGN.md' src/`）

## 难度

小。是文档收口，不改行为。**但需要先做判断（编号体系怎么定），不是纯搬运。**
