## 〇、先修正两处对现象的误读

动手前把 prd 里的描述对着代码和像素核了一遍，**有两条与事实不符**。
这两条如果照着字面改，会改错东西 —— 所以先摆证据。

### 误读 A：「两套图标体系」（prd #1 的前半句）

**不成立。** 侧栏所有图标都出自同一个基件（`app.js:12940` 的 `Svg`）：

```js
{ viewBox: "0 0 24 24", fill: "none", stroke: "currentColor", strokeWidth: "1.8", ... }
```

`IconAssistant` / `IconProject` / `IconLibrary` / `IconMore` 与
`IconSkill` / `IconAutomation` / `IconChart` / `IconStats` 是**同一种线稿**，
同为 16px、同为 1.8 描边、同为 `currentColor`。差异**纯粹是颜色**，实测：

| 走查点 | 最暗像素 | 说明 |
| --- | --- | --- |
| 「专家·技能·连接器」图标 | `rgb(0,0,0)` | `.nav-item` → `color: var(--text)` |
| 「助理」图标 | `rgb(169,169,169)` | `.nav-item:disabled` → `color: var(--text-faint)` |
| 「新建任务」的 `+` | `rgb(0,0,0)` | 与上面两项**同色**（见误读 B） |

169 落在 #f2f2f2 的侧栏上 = 30% 黑，正是 `--text-faint`。
所以「浅灰线框 vs 深色实心」是**同一个图标族在两个灰度档上的呈现**，
不是两套图形语言。**改图形是改错了地方。**

### 误读 B：「新建任务的 `+` 也是浅灰」「`+` 与文字间距偏大」（prd #2）

**两条都不成立**，但底下压着一个真的 1px 缺陷。

- `+` 的渲染色是 **`rgb(0,0,0)`** —— 与文字「新建任务」同色，与已就绪导航项同色。
  「看起来浅灰」是**光学印象**：plus 只有两笔、`stroke-width` 在 15px 下
  折算 `1.8 × 15/24 ≈ 1.13px`，ink 面积远小于文件夹 / 星芒那类图标，
  同样的黑色读起来就轻。**它是黑的，不是灰的。**
- 间距：`.nav-item, .new-task { gap: var(--space-3) }`（`app.css:1025`）——
  与下面每一项**同一个值**（8px），没有「偏大」。
- **真缺陷**：`IconPlus` 用的是 `size={15}`（`app.js:13641`），
  而导航项全部是 `size={16}`。全侧栏只有这一处 1px 不一致，
  也正是它让 `+` 的笔画比邻居再细 6%。

### 误读 C（prd 没写，但现场最严重）：能力 chip 那一行是一条**渲染 bug**，不是设计

prd #9 说「`文档处理 数据分析及可视化 深度研究 幻灯片` 独立成一条白条」。
**这条白条是 bug 的产物。**

`app.css:1818` 的注释**丢了收尾符**：

```css
	min-height: 32px;
	/* 与输入卡的间距 =          ← 注释从这里开始，没有 */
	margin-bottom: var(--space-4);   ← 被吃掉
}                                    ← 被吃掉
                                     ← 被吃掉
.capability-row::-webkit-scrollbar { ← 整条被吃掉
	display: none;
}                                    ← 被吃掉
                                     ← 被吃掉
.capability-chip {                   ← 选择器被吃掉
	display: flex;
	align-items: center;
	/* 单行布局里不许被压缩变形… */   ← 这个 */ 结束了上面那段注释
	flex-shrink: 0;                  ← 从这里开始的声明全部落进了 .capability-row
	…
```

直到 1829 行那个 `*/` 才闭合，于是从 1830 行起的所有声明
**被解析进 `.capability-row` 里**。实机 computed style 印证：

| | 本该是 | 实测 |
| --- | --- | --- |
| `.capability-row` | 纯 flex 行 | **`border: 1px #e6e6e6`、`border-radius: 999px`、`padding: 0 8px`、`background: #fff`、`font-size: 14px`、`color: rgba(0,0,0,.5)`、`gap: 4px`（本该 8）** |
| `.capability-row` 的 `margin-bottom` | 12px | **`0px`**（声明被注释吃掉） |
| `.capability-chip` | 白底细边胶囊、高 32 | **无任何基础样式**：`h=22`、`background: transparent`、无边框 |

像素也印证：CSS y=207.5 那一行有一条 **765..2322 连续不断的边框线** ——
整行是一个 800px 宽的白色胶囊。**「一条白条」就是这么来的。**

> 净括号数是**平衡**的（吃掉一个 `}`、一个 `{`，外加一条完整规则的一对）——
> 所以任何「括号配平」式的检查都发现不了它。发现它靠的是
> 「源文本里的类名 vs 浏览器解析出的选择器」这个差集（见 §七）。

**这一条不修，下面所有关于「chip 行」的讨论都没有意义。**

## 二、侧栏（#1 / #2）

### 2.1 先看决策记录

`.trellis/tasks/10-01-onboarding/design.md` 与 `docs/ONBOARDING-RESEARCH.md` §1
已经为这 4 项做过决策，**记录在案**：

> (a) 把 4 项从 `NAV_ITEMS$1` 移出，收进一个「更多」入口…**这是重组而不是隐藏**
> (b) 保留 6 项，把 `ready:false` 的渲染改成真禁用态：不加 `onClick`、
> `aria-disabled`、去掉 hover/active 反馈，**并用文字或角标说明状态**
> （`docs/DESIGN.md` §7.6「状态不只靠颜色」要求同时有文字）

已实现的是 **(b) 的一半**：`disabled`、去掉 hover/active、`cursor: default` 都落了；
**「用文字或角标说明状态」没有落**。而 `app.css:9713` 自己的注释还写着
「形态要能独立表达」—— 但它只补了 `cursor`（指针不是画面上的形态）。

所以 prd #1 的「不像刻意设计」是有据可查的**未完成项**，不是新诉求。

### 2.2 做法：补齐 (b) 的「文字」，并按 (a) 的思路做最小重组

**保留 6 项**（不折进「更多」＝信息一条不少，不碰 §6「不隐藏核心功能」），
只把 4 项未开放的**排成连续一组**，放在已就绪项之后：

```
新建任务
专家·技能·连接器
自动化
诊断
统计
即将开放                 ← .section-title（既有类，不新造）
助理 / 项目 / 资料库 / 更多   ← 仍 disabled、仍带 nav-item-pending
```

为什么必须「连续」而不只是「加个角标」：现在是 灰-灰-黑-黑-灰-灰-黑-黑，
交替出现读作**随机缺图**；连成一块 + 一个标题，读作**一个还没开放的分组**
（格式塔邻近性）。这正是 (a) 说的「重组而不是隐藏」的最小形态。

组内顺序不变；`NAV_ITEMS$1` 数组本身不动，只改渲染处的分组。

### 2.3 灰度：0.3 → 0.5

`.nav-item-pending, .nav-item:disabled { color: var(--text-faint) }` → `--text-secondary`。

两条依据，缺一不可：

1. **§2.1 的字面要求**是「停用态用**降一档**灰度」。三档是
   `--text`(1.0) / `--text-secondary`(0.5) / `--text-faint`(0.3)，
   「降一档」= 0.5。现在的 0.3 是**降了两档**。
2. **0.3 让图标消失**。16px / 1.8 描边的线稿在 30% 黑下只剩一点灰影——
   这就是「看起来没加载出来」的直接成因。状态一旦由
   **位置（连续成组）+ 文字（组标题）+ `disabled`** 三样独立承担（§7.6），
   颜色就不必再靠「淡到看不见」来表达。

e2e 只断言「未就绪与已就绪**不同色**」（`onboarding.mjs:340`），0.5 ≠ 0 仍然成立。

### 2.4 `+` 的 1px

`IconPlus size={15}` → `size={16}`（`app.js:13641`）。

**不动「同形」这条**：`app.css:1013` 写着
「「新建任务」与导航项**同形**（2026-09-19 用户要求）：它是列表里的第一行导航，
**不是黑色主按钮**」。把它改成实心主按钮 = 推翻一条有日期、有出处的用户决定。

## 三、首页垂直节奏（#3 / #9 / #6 的一半）

### 3.1 实测的现状

| 相邻两段 | 实测间距 | 档位? |
| --- | --- | --- |
| 标题底 91 → 场景胶囊顶 107 | **16** | `--space-5` |
| 场景胶囊底 143 → 能力 chip 顶 207 | **64** | **档外值** |
| 能力 chip 底 239 → 清单卡顶 239 | **0** | 不是间距 |
| 清单卡底 399 → 输入槽顶 407 | **8** | `--space-3` |

**病根可以精确定位到一行**。`app.css:1765`：

```css
	/* 场景 pills 与下方 composer 的间距原值 64px。 */
	margin-bottom: 64px;
```

这个 64 是**为「场景胶囊 → 输入卡」标定的**。后来能力 chip 那一行被插进了
这段间距里，而 64 从没被重新分配 —— 于是一段本该 64 的间隔被拆成了
「64 + 32(chip 行) + 0」，**最长的一段空白落在两个本该挨着的控件之间，
而两件不同的事之间是 0**。这就是「节奏没有关系」的全部原因。

### 3.2 新节奏：三档，四段

分组是按**语义**分的，不是按好看分的：

| 段 | 间距 | 档位 | 为什么 |
| --- | --- | --- | --- |
| 标题 → 场景胶囊 | **12** | `--space-4` | 同一个头部单元：标题是身份，胶囊是它的作用域限定 |
| 场景胶囊 → 能力 chip | **12** | `--space-4` | 同一控制簇的第二行：chip 是选中场景的**下钻**（点击弹出该场景的提示词） |
| 能力 chip → 上手清单 | **24** | `--space-6` | 控制簇结束、任务区开始 —— **全场最大的一段** |
| 上手清单 → 输入卡 | **16** | `--space-5` | 清单的第 3 行按钮写着「去写第一条 →」，它指向输入卡，所以要比 24 亲密；但必须 **> 清单内部 8px 的行距**，否则两者读成同一块 |

12 : 12 : 24 : 16 —— 只用三档（4/5/6），**不新增档位**。
`--space-7`(32) 留给模态与大弹层，这里不用。

`64px` 这个档外值随之消失，顺带补上一条档位纪律。

### 3.3 清单消失后的节奏同样成立

清单是「三项都完成即消失」的组件。它不在时，`24` 由 chip 行自己的
`margin-bottom` 提供，输入卡紧接着上来 —— 间距仍然成立，不留空洞。

## 四、清单与输入卡解耦（#4 / #5 / #8）

### 4.1 机制不是 DOM 嵌套

`.home-guide` 与 `.composer-card` **本来就是兄弟**（都在 `.composer-zone` 里，
`app.js:15901-15967`），不是父子。它们读成一张卡，是**表面 + 间距**造成的。像素证据：

```
CSS y 398-399  #e6e6e6   ← 清单卡的 1px 下边框
CSS y 399-406  #ffffff   ← 8px 纯白
CSS y 407-408  #f0f0f0   ← 输入槽的渐变起点（2px）
CSS y 409      #e6e6e6   ← 输入卡的 0.5px 边
```

**1px 边 + 8px 白 + 2px 灰 + 0.5px 边** —— 眼睛读到的是「一张卡中间一条分隔线」。

所以「解耦」的正确落点是这两条，而不是挪 DOM：
挪了 DOM 而这两条不改，画面**不会有任何变化**。

### 4.2 清单：从「又一张白卡」变成「一张抬升带」

| 属性 | 现在 | 改成 | 理由 |
| --- | --- | --- | --- |
| 底 | `var(--bg)` 白 | `var(--bg-raised)` | token 注释原文：「抬升面：**次级卡片**、选中底、代码块底」。清单是次级辅助面，用它是这个 token 的自有语义，不是新开档 |
| 边框 | `1px solid var(--border)` | **去掉** | 它是「又一张带边的白卡」的直接来源；去掉后全屏只剩输入卡一个盒子 |
| 间距到输入卡 | `--space-3`(8) | `--space-5`(16) | 必须大于清单内部的 8px 行距，否则读作同一块 |

于是首页的盒子数从 **4 个**（清单卡 + 输入槽 + 输入卡 + chip 行）
降到 **2 个**（输入槽 + 输入卡）—— 输入卡成为唯一的白卡、
唯一的阴影、唯一的渐变槽。这就是 #8 要的「视觉重点」。

### 4.3 字号：让清单退出重点争夺

清单现在的三行是 **14px / 600 / 纯黑** —— 比输入卡的 15px 占位符还重。
**抢重点的是清单，不是输入卡。** 这是 #4 / #5 / #8 的共同病根。

| 元素 | 现在 | 改成 | 理由 |
| --- | --- | --- | --- |
| `.home-guide-text`（3 行待办） | 14px / 600 / `--text` | `--text-list`(13px) / `--text` | 仍是全页最实的正文，但不再压过输入卡 |
| 第 4 行「本地优先…」 | 14px / 600 / `--text` | 新类 `.home-guide-note`：`--text-meta`(12px) / `--text-secondary` | `app.css:1923` 的注释**自己承认**「它本该用上面写的 meta 档，但没有既有的 meta 类可复用」—— 现在补上这个类 |

`.home-guide-note` 是新类名，但**没有复制任何视觉值**（§6 禁的是复制样式），
且它服务的是一个此前被注释明确点名「本该有」的档位。

高度：160px → 约 132px（省 28px，回应 #5）。

### 4.4 为什么不把清单挪出 `.composer-zone`

`.composer-zone` 是 `position: relative` 的定位容器，清单在里面**没有任何耦合语义**。
把它挪出去要连带处理 `.context-row`（清单在「三项全完成」态会渲染它）、
`align-items: center` 下子项收缩等一串副作用，而**画面一像素都不会变**。
按 `AGENTS.md` 红线 6（不为改样式动大 chunk），不做无收益的结构改动。

## 五、三个选择器（#6）

### 5.1 「分两处」不是问题

- `选择模型` 是「**这次谁答**」，属于输入动作，与发送键同排；
  对话页同样是它留在卡内（`.composer-bar` 的 trailing）。
- `选择工作空间` / `默认权限` 是**会话级配置**（在哪跑、以什么权限跑），
  不是「写」这个动作的一部分。

分布是有语义的。而且**把它们挪进卡里会撞上一条有据可依的用户决定**：
`app.css:2849` 那整段注释记录着 2026-09-18 用户实测要求
「新建任务页权限那里该是灰色」，而 `.composer-bar .permission-menu-zone .context-chip
{ color: var(--text) }` 正是按「首页在 `.context-row`、对话页在 `.composer-bar`」
这个**位置差异**写的。挪进去 = 顺手把这颗 chip 变黑 = 推翻用户实测结论。
**这正是 `.trellis/spec/workflow/index.md` 记的那类错误，不做。**

### 5.2 但有一个量出来的真缺陷：左缘错 4px

| 元素 | 左内边距 | 内容左缘 x |
| --- | --- | --- |
| `.composer-card`（`padding: var(--space-4) var(--space-5)`） | 16 | **390** |
| `.context-row`（`padding: 0 var(--space-4)`） | 12 | **386** |

两行本该在同一个左缘上对齐，差了 4px。卡里的 `+`、卡里的文字都在 390，
下面那行挂在 386 —— 这是「看着不协调」里最容易指认的一处。

**改**：`.context-row { padding: 0 var(--space-5) }`（12 → 16）。
一行改动，两行左缘合并。

## 六、案例卡（#7）

### 6.1 标题截断：成立

实测 `.case-title` 宽 **194px**、14px、`white-space: nowrap` + ellipsis。
「八十二亿之后：全球人口结构与趋势图志」18 字 ≈ 252px > 194px → 截断。

**改**：允许折两行（`-webkit-line-clamp: 2` + `white-space: normal`，
保留 `text-overflow: ellipsis`，Chromium 会在末行补省略号）。
封面的 `aspect-ratio` 与四列网格都不动，所以四张卡的封面仍然严格对齐，
只有标题区的下沿可能不齐 —— 而标题在卡片里是**最后一个元素**，不影响任何对齐。

### 6.2 不改列数

`app.css:2911` 记着「`__row`：**4 列 gap 8**（原我们 12）」—— 4 列是参照物取值。
且一页正好 4 条（`PAGE_SIZE`），改成 3 列会让第 4 条换行、把案例区撑成两行。
**不动。**

### 6.3 「缩略图占比低」：**本轮不动，如实记录**

封面是 16:9、194×109，占卡片高度 **78%**，比例本身不低。
读起来「空」是因为**封面图自身**是白底文档截图，缩到 194px 宽就是
「一块有字的白方块」。这是**素材问题，不是版式问题** ——
改版式（加大封面、换比例）治不了它，只会让四张更像白块。
（如果要做，方向是给案例换一批「有色彩对比」的封面图，属于内容侧工作。）

## 七、灰阶层次（#8）

### 7.1 平的不是「灰太少」，是「灰没分工」

实测首页的墨色清单：

| 元素 | 字号 / 字重 | 颜色 |
| --- | --- | --- |
| 首页标题 | 30 / 600 | `--primary`（90% 黑） |
| **清单三行待办** | **14 / 600** | **`--text`（纯黑）** |
| 能力 chip 文字、案例标题、案例区标题、输入占位符、context chip、模型 chip、`.section-title` | 12–15 / 400 | **一律 `--text-secondary`（50%）** |

两个病：

1. **50% 这一档承担了几乎所有角色** —— 标签、说明、标题、占位符全在一档。
2. **唯一比它更强的正文级元素是「上手清单」**，所以输入卡不是重点。

### 7.2 表面阶梯也平（登记，不改值）

| token | 白底上的值 | 相邻差 |
| --- | --- | --- |
| `--bg` | 255 | — |
| `--bg-raised` | 247 | 8 |
| `--bg-hover` | 242 | 5 |
| `--bg-chip` | 240 | **−2（比 hover 还深）** |
| `--border` | 230 | 10 |

`--bg-chip`(6%) **比** `--bg-hover`(5%) **深** —— 静态 chip 底比 hover 底还重，
方向是倒的。这是**系统内既有的一处倒挂**，牵动全站组件，
**本轮只登记、不改值**（改它会让 hover 反馈在所有 chip 上反向）。

### 7.3 改法：不加一个颜色，只拉开明度关系

全部靠**已有 token 的重新分配**完成：

1. **清单退出竞争**（§4.3）：14/600/纯黑 → 13/`--text`；说明行 → 12/`--text-secondary`。
2. **清单换到 `--bg-raised`**（§4.2）：首页第一次出现「白卡之外的第二种面」。
3. **去边框**（§4.2）：盒子的数量从 4 降到 2，剩下的那个（输入卡）自然成为重点。
4. **节奏拉开**（§三）：24 与 16 两档给了呼吸。

于是首页首次有四级可读层次：

```
30px 标题  →  13px 待办  →  12px 说明  →  15px 输入区（唯一的白卡 + 唯一的阴影）
```

### 7.4 chip 行**不重新上色**

`app.css:1831` 记着 chip 取自参照物的 `.quick-actions__item`：
「高 32、padding 0 12、gap 4、14px/400、文字二级色、**白底细边**、胶囊圆角」
—— 「白底细边」是有出处的取值。而且现在看到的样子**根本不是它**（见 §〇-C）。
正确动作是**把 bug 修好、让记录的样式真的生效**，而不是在被 bug 破坏的画面上再做设计。
它的「割裂」由 §三 的节奏解决。
