## 1. 结论

**判断：不阻断发布，但「时限」那一组有一处会误导人的实现，建议发布前修掉。**

一句话：**提案的骨架被忠实实现了** —— 位置对、类名复用对、禁用态真的禁用了、
报告六态真的分开了、零新增 Token 档位，浅色与深色两张图都能读；
但「时限」这一组的**控件语义在实现时被换掉了**（提案是「4 个 chip」，实现是
「3 个 chip + 1 个数字输入框」，而那个输入框长得和第 4 个 chip 一模一样），
它现在同时制造了「默认全是禁用态」的观感（第 2 问）和一条**静默吞掉用户输入**的路径
（§3.2），而后者恰好是本功能最不能犯的那类错。

「不阻断」的理由：静默吞输入这条路要用户主动把数字填成 0 或 200 才会走到，
而 daemon 侧 `parseWatchPolicy` 对它**会抛错**（不是静默折算），用户不会带着
一个坏规矩跑一整夜。它是「该修」而不是「必须挡发布」。

## 3. 我确认看到的问题（有截图或代码证据）

### 3.1 「时限」的四个 chip 里，第四个不是 chip，是输入框 —— 但长得完全一样

**现象。** 截图 `watch-rules-form-light.png` 底部「时限」一行：
`15 分钟` `30 分钟` `60 分钟` 三颗灰底的圆角小方块，右边紧跟一颗写着 `自定义` 的
同样灰底圆角小方块。**四颗看起来是同一族的按钮。**

代码里它们不是：前三个是 `<button className="num-chip">`（`app.js:69069-69081`），
第四个是 `<input type="number" className="num-chip-input" placeholder="自定义">`
（`app.js:69082-69095`）。CSS 上 `.num-chip-input` 是**照抄** `.num-chip` 的观感写的
（`app.css:10302-10312`，注释原话：「与 .num-chip 同款，否则『自定义』那个框会比旁边的预设高出一截」）。

对照提案 `ux-proposal.md:63`：原本写的是 `.num-chip ×4（30 / 60 / 120 / 不限）+ 数字输入`，
且「自定义档才出现的数字输入」是**在第 1 行下面另起**的（提案 §1.2 的 JSX 里
`{customMinutes && (<input id="auto-watch-minutes" …/>)}` 在 `.num-chips` **之外**）。

**为什么这是问题。** 用户的心智模型是「四个预设，点哪个选哪个」。第四个**能点进去打字**，
但它的外表在静止态和另外三个**完全无法区分**：没有输入框的底色差、没有边框差
（`.num-chip-input` 与 `.num-chip` 都是 `background: var(--bg)` + `border: 1px solid var(--border)`）。
一个用户想设 45 分钟，看到四个一模一样的方块，会先依次点前三个看有没有 45 ——
点不到，然后才可能想到第四个是输入框。**这是「外观说谎」的那一类问题：
控件的可交互方式没有被它的形态预告出来。**

**代价。** 不致命，但它是本组唯一的「摸索成本」。对比同屏的「能力」组：
`.preset-item` 是整行带描述的大块，一眼就知道是三选一，不会和别的东西混淆。
「时限」这行四颗小方块则要求用户去试。

**怎么改（不动档位、不新增类）。** 二选一，都不引入新 Token：

- **改法 A（推荐，最小改动）**：让第四颗**读起来是输入框**，而不是靠加字。
  给 `.num-chip-input` 去掉那行刻意的同款声明，改用它本来就该有的档位 ——
  即 `.field input[type="text"/"number"]` 已经登记的那一套
  （`app.css:7952` 附近同族：`padding: var(--space-2) var(--space-3)`、
  `background: var(--bg)`、`font-size: var(--text-list)`）。
  **代价**：它会比旁边三颗 chip 高约 4px（`--space-2`(6) vs chip 的 `2px` 上下内距）。
  这个「高度不齐」恰恰是**有用的信号** —— 它告诉用户「这个和那三个不是一类」。
  提案当初担心的「高出一截」在当前语境下是**症状而不是缺陷**：
  三颗预设 + 一个输入框本来就是两种控件，抹平高度才是伪装。**我主张让它高出来。**
- **改法 B**：保持同高，但把 `placeholder` 从 `自定义` 改成 `自定义分钟数` ——
  至少让静止态的字透出「可以输入」。
  **代价更小，但只解决了「不知道能输入」，没解决「四颗长得一样」的误导。**
  如果只做一条，做 A。

> **不要**在这里新增第五颗 chip 叫「不限」（提案原本有）。「不设时限」已经是
> 默认态（`emptyDraft` 里 `watchMinutes: ""`），再给它一颗 chip 会造出
> 「未选中任何 chip = 不设时限」和「点『不限』= 不设时限」两条等价路径 ——
> 这正是提案 §2.1 自己反对的「能碰到但选完折算回原值」的同构问题。

### 3.2 `自定义` 填 0 或 200：会被**静默丢掉**，界面上一个字都不说

**现象（代码证据，不是猜测）。** `draftWatch`（`app.js:67847-67858`）：

```js
const minutes = Number(draft.watchMinutes);
if (draft.watchMinutes !== "" && Number.isFinite(minutes) && minutes > 0) {
  watch.minutes = minutes;
}
```

而那个输入框只写了 `min: 1, max: 120`（`app.js:69087-69088`）——
`min`/`max` 在**手输**时**不拦提交**，只在微调箭头和表单校验里起作用；
`save()`（`app.js:68730-68756`）校验了名称、内容、工作目录、调度，
**对 `watch` 一个字都没校验**，直接把 `draftWatch(draft)` 的产物交给
`window.kami.saveAutomation`。

于是：

| 用户填 | `draftWatch` 的结果 | 界面表现 | daemon |
| --- | --- | --- | --- |
| `0` 或 `-5` | `minutes` **不进 `watch`**；若其余三项也空 → `watch` 为 `null` → **规矩被整条清掉** | 直接关弹层、列表刷新，**无任何提示** | 收到 `null`，规矩清空 |
| `200` | `watch.minutes = 200` | 同上，无提示 | `parseWatchPolicy` 抛 `值守规矩的时限最长 120 分钟`，保存失败，`ErrorState` 显示 |

**为什么这是问题。** 这一条**正是本功能存在的理由的反面**。提案 §2.1 的判据原话是
「误会的成本高于困惑的成本……本题要防的是前者」。填 `200` 时 daemon 会拒绝，还算好；
填 `0` 时是**真静默**：用户以为设了「立刻超时」的极限保护，实际 `minutes` 根本没落盘，
运行走的是**内置 30 分钟兜底**（`session-files.js:1092-1093`）。
两条路径的用户处境不同，但都属于同一类：**界面接受了一个它并不打算照做的输入。**

**怎么改（落在已有类上）。** 在 `save()` 里、`buildSchedule` 之后补一段与
`buildSchedule` 同形的预校验，复用已有的 `setFormError`（`ErrorState` 是已注册的错误通道）：

```js
// 值守规矩的时限：与 daemon 的 parseWatchPolicy 同一条判据（1⋯120）。
// 在保存前就拒掉，不让 draftWatch 把它悄悄吞掉 —— 「填了 0 却什么都没设」
// 是本功能最不该有的失败形态。
const rawMinutes = draft.watchMinutes.trim();
if (rawMinutes !== "") {
  const m = Number(rawMinutes);
  if (!Number.isInteger(m) || m < 1 || m > 120) {
    setFormError("值守规矩的时限要填 1 到 120 之间的整数分钟；不想设时限就把这一格留空。");
    return;
  }
}
```

**代价。** 加 4 行校验 + 一句文案；与 daemon 的 `WATCH_MAX_MINUTES = 120`
（`watch-policy.js:47`）形成第二处「同一个数字写两遍」——
但它与 `watch-report-core.js` / `watch-policy.js` 那对**已经存在的镜像**
是同一性质，项目已有这条纪律（`watch-report-core.js:12-22` 的注释专门论证过）。
**不要把 120 硬编码**：如果能从渲染层可达的地方拿到这个常量就用它，拿不到就
在注释里点名 `watch-policy.js:47`，与既有镜像的做法一致。

### 3.3 运行报告里那条证人，是**写给模型的**，却整段出现在用户看的报告里

**现象。** 截图 `watch-run-report.png` 的报告体（`.run-report` 内框）：

> 越界即停：碰到值守规矩 1 次，当场停下了。
> • `write` —— 本任务设置了「只读」值守规矩：不允许修改任何文件。如果这次运行确实需要写入，**请把这个定时任务的「能力」改成「可写」，或把全局权限档位放宽到「只能改工作区」。**

这段 `detail` 的来源是 `src/main/daemon/watch-policy.js:270-272` 的 `reason`，
经 `session-files.js:1033`（`detail: verdict.reason`）进 `boundary.exceeded`，
再被 `app.js:68982` 的 `{item.detail}` **原样**渲染。

**这段文字里有两句是互相矛盾的收件人：**

1. 「**不允许修改任何文件**」—— 给模型看的，模型据此知道该放弃这条路；
2. 「**请把这个定时任务的『能力』改成『可写』，或把全局权限档位放宽到『只能改工作区』**」——
   **给用户看的**。模型没有权限改任务的「能力」，也不该去改 —— 这是只有人在
   「设置 → 权限」里能做的动作。

**为什么这是问题。** 三条代价：

- **对用户**：报告里出现一句「请把……改成『可写』」。用户照做的后果是
  **放宽了自己的安全设置** —— 而这恰恰是本功能存在的目的（「只能更严」）。
  一条安全功能的失败报告在**教用户降低安全档位**，这是方向性错误。
  更实用的问题是：这句话在当前上下文里**没有动作可以执行**（报告是只读的，
  没有跳设置页的入口），用户读完只知道自己该做点什么，但不知道在哪做。
- **对模型**：`detail` 的文案在 `watch-policy.js` 里是**运行时回给模型的 reason**
  （`session-files.js:1179` `return { block: true, reason: verdict.reason }`），
  它必须对模型说得清楚。**这一段是对的，不要动它。**
- **两份收件人共用一份字符串，是这处缺陷的根因。**
  `ux-proposal.md:253` 早就写下了正确的原则：「从 daemon 的 `notes[]` **原样翻译**」
  ——注意是**翻译**。但实施在 `RunReport` 里对 `exceeded[].detail` 做的是**直出**。
  `notes` 走了 `watch-report-core.js` 的翻译通道，`exceeded[].detail` 没有。

**怎么改。** 在 `watch-report-core.js` 里加一个与 `reportLine` 同性质的翻译函数，
**只作用于渲染**，不碰 daemon：

```js
/**
 * 越界证人那句话 —— daemon 的 reason 是**回给模型**的（它必须告诉模型
 * 「此路不通，换条路」），里面那句「请把任务的『能力』改成『可写』」
 * 是给**人**的指示，模型执行不了。整段直出会让用户在失败报告里读到
 * 「请放宽你的权限档位」—— 安全功能反过来教用户降低安全设置。
 *
 * 所以这里做的是**给用户重述**：保留「哪条规矩拦的、拦了什么」，
 * 把「请你去改设置」换成陈述句。模型那一份原文一个字不改。
 */
export function witnessLine(detail) { … }
```

渲染时 `{witnessLine(item.detail)}`（`app.js:68982`）。

**文案（全文，按三条规矩各给一句）：**

| `rule` | 给用户看的重述 |
| --- | --- |
| `tier`（只读档拦下写入） | `` `write` 被拦下：本任务是「只读」档，不允许修改任何文件。`` |
| `scope`（范围外） | `` `write` 被拦下：路径不在本任务声明的可写范围内。`` |
| `outside`（工作区外） | `` `write` 被拦下：路径在本任务的工作目录之外。`` |

**代价 — 这一条我要明说，因为它不便宜。** 目前的 `exceeded[]` 条目只有
`{at, tool, detail}`（`watch-policy.js:333` 的 `appendExceed` 原样收 `verdict`），
**`rule` 字段没有落进 boundary**（`session-files.js:1033` 只挑了 `verdict.reason`）。
所以有两个选择：

- **改法 A（便宜，推荐先做）**：不动数据契约，`witnessLine` 拿不到 `rule` 时
  **不做整句重写**，只做一件事 —— **把那句给用户的指示（「请把……改成……」）
  从展示用的那句话里裁掉**，保留前半段的规矩陈述。
  用「在第一个『如果这次运行』处截断」这种规则很脆（文案一改就失效）；
  更稳的是**在 daemon 侧把 reason 拆成两半**：给模型的 `reason`（含指示）与
  给报告的一句话，各一个字段。**这就要动 `watch-policy.js` 与 boundary 的形状。**
- **改法 B（彻底，成本高）**：让 `verdict` 的 `rule` 落进 `boundary.exceeded` 条目，
  渲染层按 `rule` 出上表的三句话。**代价**：动 `session-files.js:1033` 与
  `appendExceed`，并且**老记录没有 `rule`**，渲染层必须有一个「读不到 `rule` 就
  退回展示原始 detail」的兜底 —— 那个兜底会把用户重新暴露给「请放宽权限」这句，
  所以 B 单独做也不完整。

**我的建议**：A + B 一起（daemon 多给一个 `reportReason` 字段，
渲染层有就用、没有就退回 `detail`）。这是一处**跨进程契约的小改**，
值得在本次一并做 —— 因为它是唯一一处「安全功能的界面在教用户降低安全」的地方。

### 3.4 表单被视口底部截断（第 1 问的事实基础）

**现象。** `watch-rules-form-light.png`（以及深色同一屏）：
`.auto-form-card` 从窗口顶部上方开始（标题「新建定时任务」贴着顶端，
y≈37px 处已是被裁的位置），到窗口底部被切断 —— 「能力」组里
「可写」这一行**只露出标题『可写』两个字，副行描述被切在视口之外**。
`.save-space-actions`（取消/保存）**完全看不见**。

**这是既有结构，不是本功能引入的。** `.modal-backdrop`（`app.css:8669`）是
`align-items: center` + `padding: var(--space-6)` 的居中容器；
`.auto-form-card`（`app.css:10216-10236`）是 `max-height: 100%; overflow-y: auto`。
所以卡片**有内部滚动**，滚到底能看到「可写范围」「越界即停」和保存按钮 ——
**功能是完整的，没有东西不可达**。截断的是**首屏**。

**为什么这是问题（且是本功能把它推过临界点的）。** 本功能**新增了这一组四个声明**
（时限/能力/可写范围/越界即停），把卡片内容推高了约一屏的 1/3。
在加它之前，`AutomationForm` 的 6 个 `.field` 在一屏里基本放得下；
现在**保存按钮掉到了首屏之外**，用户填完任务内容后**看不到「保存」在哪** ——
必须自己意识到要滚。

而这一屏最危险的位置恰恰是**被切掉的那半行**：「可写」的副行描述
（`readOnlyGlobal ? "当前全局是「只读」，本任务的「可写」不会放宽它。" : "工作空间内自由读写。"`）
是本功能「只能更严」立场的**唯一一句就地解释**。它在首屏被切掉一半 ——
用户看到「可写」两个字，看不到后面那句「不会放宽它」。

**怎么改（不违反 DESIGN.md 档位纪律）。** 三条路，按代价排序：

- **改法 A（不动结构，零风险）**：给 `.auto-form-card` 加**吸底的保存条**？
  **否。** 那要给卡片内部再切一层布局、给 `.save-space-actions` 加 `position: sticky`
  与背景/边框补丁，是**新的盒子**（§3.9 盒子预算），而且会与「遮罩不响应点击关闭」
  的既有决定打架。**我不推荐。**
- **改法 B（只改一处既有声明，推荐）**：`.modal-backdrop` 现在是
  `align-items: center`（`app.css:8673`）。改成 `align-items: flex-start` +
  保留 `padding: var(--space-6)`，卡片就会**顶部对齐**，从标题开始完整显示。
  **但它把问题从「底部切」变成「顶部切」**（内容超一屏时底部照样切），
  只是把**开头**（标题、名称、任务内容——用户最先要看的东西）保住了。
  代价：影响 `.modal-backdrop` 的**全部消费方**（权限弹窗、MCP 表单、模板选择浮层）
  —— 这是四个消费方的共同背板，改它要回归四处。**改动只有一行，但影响面是四屏。**
- **改法 C（本功能自己收窄，最稳）**：当前「能力」三项各占 `padding: var(--space-3) var(--space-4)`
  + 两行文字（`app.css:7861`），约 60px 一行、三项 180px。
  **这一组的描述文字对本功能是有价值的信息，不能砍。** 所以能省的是**节奏**：
  `.watch-group` 现在 `gap: var(--space-2)` + `margin-top: var(--space-3)`
  （`app.css:10289-10294`），已经是最紧的了，**没有可省的空间**。

**我的结论：改法 B 是对的那个，但必须由**产品**决定「四个消费方一起顶对齐」是否可接受。**
如果只在自动化页顶对齐（给 `.auto-form-card` 单独写 `align-self: flex-start`），
代价降到「只影响这一个弹层」，且**语义上说得通**：
这个卡片是四个里唯一内容会超过一屏的，它本来就该顶对齐。

```css
/* 表单内容比 permission-card 多得多，居中会让「保存」落在首屏之外；
   顶对齐保住标题与前面的字段（自动化的表单是全站最长的弹层）。
   只挑这一个消费方，不动 .modal-backdrop —— 另外三屏内容短，居中是对的。 */
.auto-form-card {
	align-self: flex-start;
}
```

**代价**：`align-self` 需要在 `.modal-backdrop` 的 flex 容器里生效，
而 `.auto-form-card` / `.mcp-form-card` / `.mcp-editor-card` 是**同一条规则**
（`app.css:10216-10219`）—— 所以要么把 `.auto-form-card` 从那条并集里拆出来，
要么给并集加、让三个表单都顶对齐（MCP 表单短，顶对齐会让它贴顶、观感变差）。
**拆选择器是必须的，这是本条的隐蔽代价，实施时别漏。**

## 4. 必须回答的三个具体问题

### 4.1 表单在 1280×720 被截断：这个滚动可接受吗？该改结构吗？

**答：滚动本身可接受（不能改成「一屏塞下」，那要砍掉本功能唯一的就地解释）；
但「居中布局」应该改，改法是给 `.auto-form-card` 单独 `align-self: flex-start`。**

理由分三层：

1. **滚动不可消除。** 卡片里现在有 10 组内容（名称/任务内容/调度/时刻/工作目录/时限/能力/
   可写范围/越界即停/按钮）。要一屏放下的唯一办法是砍内容 —— 砍掉「可写范围」或
   「越界即停」的副行描述，那正是本功能的解释性文字。**用滚动换信息的完整，这笔交易是对的。**
2. **但「居中」让首屏丢掉的是开头而不是结尾。** 居中的卡片在内容超高时，
   **顶部和底部同时溢出**，用户第一眼看到的既不是标题也不是保存按钮 ——
   看到的是**中间一段**。这是最差的切法。顶对齐至少让用户从「名称」开始读。
3. **改法不违反档位纪律**：`align-self` 不是 Token，它不引入任何间距/字号/圆角/阴影档位。
   它只改变既有元素在既有 flex 容器里的对齐 —— **§2 的档位表一个字都不用动**。

**代价（必须写明）**：`app.css:10216` 是 `.auto-form-card, .mcp-form-card, .mcp-editor-card`
的并集规则。要只让自动化表单顶对齐，**必须把 `.auto-form-card` 从并集里拆出来单独写** ——
这会增加一处重复（宽度/内边距/阴影等声明要么抽公共、要么两处写）。
**如果嫌拆选择器代价大，退而求其次是在并集上加** —— 代价是 MCP 表单与 JSON 编辑器
（内容短）也会贴顶，从居中变成顶部留白，观感是「松了」而不是「坏了」。
**两条路都比现在的「保存按钮掉出首屏」好。**

### 4.2 「时限」四个 chip 在默认态下**全是禁用态**——会不会让用户以为功能坏了？

**先纠正一个事实（我要避免跟着前提走，因为这个前提与截图不符）：**

**截图里那四颗不是「禁用态」，是「静态态」。** 证据：

- `watch-rules-form-light.png` 里 `15 分钟` `30 分钟` `60 分钟` 的字色**比**
  同屏的禁用态元素**深**。同屏 `.preset-item:disabled` 的「可写」走 `opacity: 0.55`
  （`app.css:7874`），它的字明显更淡；三颗 chip 的字没有这层淡化。
- **`自定义` 那一颗是明显可用的**：它的字色最深，而且在深色截图
  `watch-rules-form-dark.png` 里它是**唯一被强调**的那一颗（有更亮的底/边）。
  这说明「三颗灰、一颗亮」是**同一行里的对比**，不是全行禁用。
- 代码侧：`.num-chip` 的静态字色是 `--text-faint`（`app.css:8079`，
  「弱文：禁用态文字、禁用态占位符、最弱图标」—— 这个 token 的**语义就是**最弱一档），
  而 `disabled` 才额外叠 `opacity: 0.55`（`app.css:10315`）。
  **也就是说：三颗 chip 在默认态下，用的是「和禁用态同一个色阶」的颜色。**

**这才是真问题，而且比「全是禁用」更微妙：**

> **`--text-faint` 的语义被登记为「禁用态文字」，而 `.num-chip` 在可用状态下
> 就用它 —— 于是「可用的未选中 chip」与「禁用 chip」在颜色上无法区分。**
> 用户确实可能把这三颗读成「不能点」。**但这不是把默认态做成了禁用态，
> 而是把一个可点的控件画成了禁用态的颜色。**

**为什么这是问题。** 本功能的立场是「禁用态是要被读出来的」（提案 §2.2 的核心）。
当一个**可点**的 chip 和**不可点**的选项共享同一种淡色时，「灰 = 不可用」这条
用户已经学会的规律在这里失效了 —— **它削弱的是「禁用态」这个信号本身的可靠性**，
而不只是让这三颗 chip 难看清。代价是双向的：用户可能点不到本该能点的
（以为坏了），也可能在真正禁用处不以为意（因为「灰的也能点」）。

**怎么改（不新增档位）。** `.num-chip` 的静态色从 `--text-faint` 提到 `--text-secondary`
（`app.css:8079`）。**代价**：

- 这**不是本功能引入的**规则（`.num-chip` 在别处已用，`app.css:8064` 附近有它的
  使用先例），所以改它**会影响其他消费者**。**必须先查清 `.num-chip` 的全部使用点**
  —— 我只确认了它在本功能里的用法，**没有审计它的全部消费方**（这是本文 §5 的一条
  「怀疑但未证实」）。
- 如果审计结果是「只有本功能在用」，这个改动就是安全的、一行的事。
- 如果还有别处在用，**退而求其次**：不动 `.num-chip` 的基础色，而是让
  `WatchRulesField` 里那三颗 chip 用 `.num-chip` + 一个**已登记的**强调状态 ——
  但那需要新类名，**违反「落在已有类上」的约束**，所以**我不推荐这条退路**。
  真要退，宁可接受现状（把 `--text-faint` 理解为「未选中的弱化」而非「禁用」，
  并在 `docs/DESIGN.md` 里把这条关系写清楚）。

**对「用户会不会以为功能坏了」的直接回答：** 不会坏到「以为功能坏了」的程度 ——
因为旁边那颗 `自定义` 是明显亮的，一行里有可点的东西，用户不会判定整组失效。
**但会让人多试探一次。** 这是「该修但不阻断」的一类。

### 4.3 那条越界证人是给谁的？放在用户看的报告里合适吗？

**答：它是给模型的（证据确凿），但当前它同时也是给用户的（因为文案里混进了
一句只有人能执行的动作）。二者必须拆开 —— 详细证据与改法见 §3.3。**

补三点判断：

1. **「给模型看」本身不是问题。** 用户看这份报告时想知道的是
   「谁越的、哪条规矩拦的、拦下之后发生了什么」。`write` 这个工具名与
   「不允许修改任何文件」这句对用户**都是有信息量的**（PRD 的痛点原话是
   「用户回来只能翻台账看一行成功/失败」——现在的报告比那强得多）。
   **原样保留规矩原文是正确的。**
2. **不合适的是第二句。**「请把这个定时任务的『能力』改成『可写』，
   或把全局权限档位放宽到『只能改工作区』」——**这一句在给用户看的报告里
   是反向的**：本功能的价值是「只能更严」，报告却在建议用户放宽。
   而且它是**对模型的指令语气**（「请把……」），读起来像界面在指挥用户。
3. **这一处恰好也是「给模型的 reason 与给用户的解释共用一份字符串」的典型症状** ——
   项目在 `watch-report-core.js:12-22` 已经为「判定」建了镜像纪律，
   但「文案」这一层还没建。**`witnessLine` 就是补这一层。**

> **`stopped` 的徽标文案**：`watch-report-core.js:114` 写的是 `超时中止`，
> 报告体首行 `watch-report-core.js:92` 写的是 `被叫停：运行超过了设定的时限。`。
> 提案 §4.2 要求 `timedOut` 的徽标是 **`被叫停`**（原话：「必须是 `被叫停`
> 而不是 `失败`」）。实现的 `超时中止` **满足提案的意图**（它确实不是「失败」）
> 但**与提案逐字文案不符**，且与报告体首行的「被叫停」**不同词**。
> 同一次运行在两处叫两个名字，用户要多想一步才能把它们对上。
> **建议统一为「被叫停」**（改 `watch-report-core.js:114` 一处，
> 检查 `watch-report.test.mjs` 里是否有锁定 `超时中止` 的断言）。
> **代价极低**（一个字符串），**收益是消掉一次不必要的核对**。

## 7. 明确「不许改」的部分（防止下一轮顺手放宽）

- **`.preset-item` 的 `disabled` 机制不许改。** 它是本功能的立场本身。
  不要因为「灰着不好看」把它换成「可点 + 事后告警」—— 提案 §2.1 论证过那更糟。
- **「不生效」徽标不许删。** 它是「状态不只靠颜色」的**文字通道**；
  `opacity: 0.55` 单独存在时，用户读不出「为什么」。
- **越界证人的规矩原文不许删。** 用户需要知道是哪条规矩拦的。
  要改的只是那句「请把……改成……」的**指示**（§3.3）。
- **报告里不出现 `暂无` / `无记录` 类句式。** `ok` 态的首行是
  「跑完了，一次都没越界。」—— 把零说成一件完成的事。这是刻意的。
- **老记录不渲染报告体。** 不编空 boundary。
- **不许给 `resources/**` 提建议。**（本次评审没有涉及，此处仅作声明。）

## 10. 追加裁决：表单里的「事前折算说明」补还是记缺口

> 本节回应 Lead 于本文交付后的追问，**只回答这一个问题**。
> 涉及 `tierLocked` 的既有章节以 §5.4 / §5.5 为准，**本节取代它们对 `tierLocked` 的判断**。

### 10.0 先认一处错：我把 `自定义` 读成了 chip

Lead 的取证是对的。`app.js:69082-69095` 那颗是 `<input className="num-chip-input">`，
「自定义」是它的 **placeholder**；三颗 `num-chip` 按钮（`app.js:69069-69081`）
**都没有 `disabled`**。我在 §4.2 说「`自定义` 是明显可用的、所以一行里有可点的东西」
——**那句是我看错了**：它之所以亮，是因为它是**输入框**（有 `.num-chip-input` 自己的
`background: var(--bg)` + `border: 1px solid var(--border)`），不是因为它是唯一可点的 chip。

**这让 §4.2 的结论更糟而不是更好**：四个控件**全部可点，却全部被画成禁用色**
（三颗 chip 走 `--text-faint`，而 `DESIGN.md:59-60` 把 `--text-faint` 登记为
「禁用态文字」，且降到它是**降两档**）。Lead 已按 (a) 把 `.num-chip` 静态色提到
`--text-secondary` 修掉，那是对的一步。**我 §4.2 的推理链是坏的，落点是对的** ——
这一点我在 §5.1 写「没有审计全部消费方」，Lead 补上了（模型设置页
`app.js:64177` / `64200` 也在用），所以这处修复**范围超出本功能**、必须在 PR 里
如实说明，Lead 已经这么做了。

### 10.1 裁决：**本轮不补，如实记成已知缺口 —— 但要把「不补」写进代码注释。**

**理由（三条，按分量排序）：**

**一、它不是安全缺口，补它不换来任何安全增量。**
`.preset-item` 的 `disabled`（`app.js:69102`）已经**在输入口**挡住了「比全局更宽」的选项 ——
**新建流程里用户根本选不出**一个会被折算的组合。`.watch-warn` 覆盖的那条编辑路径
（历史存过 `workspace-write`、之后全局变只读）里，「可写」虽 `disabled` 但**已被选中**，
此时 `tierLocked` 为真、那行字会出现，**用户能看到「不会放宽它」**。
也就是说：**「能碰到、选完静默折算」这个最危险的形态，已经被禁用态堵死了。**
折算说明是提案自己定义的**「兜底，不是主通道」**（提案 §2.2 第二层；
`app.js:69043` 的注释也原样抄了这句）。**兜底层没做全，不等于主通道失守。**

**二、补它的代价远超它现在的收益，而且代价是「新建一份判定」。**
提案 §2.2 明确要求文案**「从 daemon 的 `notes[]` 原样翻译，不许渲染层另判一遍」**
（引 `design.md:3.2`：两份判定的漂移正是「参数被接受却不生效」的温床）。
**但今天的渲染层拿不到 `notes[]` / `warnings[]`：**

- `effectivePolicy` 只在 daemon 侧被调用（`session-files.js:1021`）；
  渲染层 `app.js` 里对它的唯一提及是**一句注释**（`app.js:69038`）；
- `warnings[]` 唯一的去向是 `boundaryFor`（`watch-policy.js:366-367`）合进
  `boundary.notes`，**只在运行结束后**出现在运行报告里；
- `listAutomations` 回来的任务记录里**没有**收敛结果（`grep` 无命中）。

**所以「补上」实际只有两条路，都很贵：**

- **(i) 让渲染层自己算一遍**（即提案的 `effectiveLineText({picked, effective, globalTier})`
  在客户端按全局档位推导）。这就是**造第二份判定** —— 恰好是提案引 `design.md:3.2`
  要防的那件事。而且 daemon 侧 `globalTier` 是**每次运行现读**的
  （`session-files.js:1006-1007`），渲染层那份是**打开表单那一刻的快照**；
  用户在弹层开着时改全局档位，两者就漂移 —— **而漂移的后果正是「界面说的和实际执行的不是一回事」**。
- **(ii) 让 daemon 把收敛结果回给渲染层**（`listAutomations` 带 `warnings[]`，
  或新增 `previewWatchPolicy`）。这是**跨进程契约新增**，且表单现在是**纯本地草稿**
  （`draft` 在 `onChange` 里 patch），要做到「改动即预览」就得把每次选点都过一趟 IPC。
  **代价与收益完全不成比例。**

**三、「如实记缺口」本身是有信息量的，而「临时补一个近似品」是有害的。**
§10.2 说清为什么 `.watch-warn` 这种近似品**不能**拿去顶替。

### 10.2 `.watch-warn` 保留还是删掉？—— **保留，但它现在的文案是错的，必须改。**

**保留的理由**：它覆盖的正是**唯一真正需要它的那条路径**（编辑一条「存过可写、
现在全局只读」的任务）—— Lead 对第 2 点的取证把这一点钉死了。删掉它，
那条路径就**完全没有事前提示**了。

**但它现在说的是另一件事。** `app.js:69195` 的文案是：

> 当前全局档位更严，本任务的「可写」不会放宽它 —— 实际仍按只读执行。

同一个屏上，「可写」那一项的 `hint` 已经写着（`app.js:69057`）：

> 当前全局是「只读」，本任务的「可写」不会放宽它。

**两句重合的部分是「本任务的『可写』不会放宽它」—— 一模一样的十二个字。**
这就是「多个入口说一件事」的实际形态：**不是互补，是重叠，而且 `.watch-warn`
那遍还带 `--danger` 红色。** 用户读到同一件事两遍，第二遍更红 ——
**红色没有增加信息，只是把「不会放宽」这个正常结论渲染成了错误。**

**改法（只改文案，不动类、不动 Token）：**
把 `.watch-warn` 从「复述结论」改成「指出去路」—— 这正是提案 §2.2 表里第一条
唯一不可省的那半句（提案 `ux-proposal.md:263-265` 原话：「**『要真正可写，请先到
『设置 → 权限』』是必写的**；只说『不会放宽』是一个死胡同」）：

```js
tierLocked && /* @__PURE__ */ jsxRuntimeExports.jsx("span", { className: "watch-warn", children: "这个任务存的是「可写」，但当前全局是「只读」—— 运行时会按只读执行。要让它真的可写，请先到「设置 → 权限」把全局档位改掉。" })
```

**代价**：一句字符串。**但它顺带修掉 §5.5 那条存疑项**：`.watch-warn` 用 `--danger`
在提案里是被明确否掉的（提案 §2.2 第三层：「它不是错误（没有东西坏了），
所以**不用 `--danger`**」）。我 §5.5 把它降级成「怀疑」—— 现在证据齐了
（编辑路径可达），**它是真的**。若改用上面这句「指出去路」的文案，红色的语义
从「出错了」变成「这里需要你做一个动作」，**`--danger` 勉强说得通；
但按提案我仍建议改成 `--text` + `--accent` 左轨**（同 `.watch-effective-narrowed`
那套，`app.css` 里已登记）。**只想改一处就改文案；两处都改更好。**

### 10.3 如果一定要补：最小可行形态 = **不做 `.watch-effective`，只补 `hint` 的缺的半句**

我**不同意**补成 `.watch-effective` 那一行。理由：

- **`.watch-effective` 的场景已经被 `disabled` + `不生效` 徽标承担了。**
  提案 §2.2 的判据表（`ux-proposal.md:213`）自己写的是「禁用**是主通道**，
  同一位置再用一行把折算结果说死」；`S1` 场景要求三件事同时成立 ——
  `.preset-item` 命中 `disabled`、徽标文本 `不生效`、`.watch-effective` 含
  「不会放宽它」与「设置 → 权限」。**前两条已实现，第三条的「不会放宽它」
  已经写在那一项的 `hint` 里**（`app.js:69057`）—— **唯一缺的是「设置 → 权限」那半句去路。**
- **所以最小可行形态不是「加一行」，是「把 `hint` 补全那半句去路」**：

```js
hint: readOnlyGlobal ? "当前全局是「只读」，本任务的「可写」不会放宽它。要真正可写，请先到「设置 → 权限」改全局档位。" : "工作空间内自由读写。"
```

**代价**：一句字符串，**零新类、零新 Token、零新文件、零跨进程契约**。
**但它有真实副作用**：`.preset-item` 的副行变长，**「能力」三项会被撑高**
—— 而 §3.4 已指出表单在 1280×720 被视口截断。**这两条建议会互相打架。**
我倾向：**先做 §3.4 的顶对齐，再动这句 hint。** 顺序反了会把首屏推得更糟。

### 10.4 放哪个文件：**同意不新建 `watch-policy-core.js`，但也不该放进 `watch-report-core.js`。**

**同意的一半**：**不新建 `src/renderer/src/watch-policy-core.js`。**
渲染层已有 5 个 `*-core.js`（`command-palette` / `file-history` / `projects` /
`trace` / `watch-report`），再加一个的边际价值确实要论证；而按 §10.1
**本轮根本不补这个翻译层**，那个新文件会是一个**消费者都不存在**的模块。
**为一个不存在的调用方建文件，是最典型的过早抽象。**

**不同意的一半**：即便将来补，**它也不该进 `watch-report-core.js`。**
那个文件的职责在它自己的头注释第 1-2 行写得很清楚：
**「把一次运行的 `boundary` 读数归约成界面上的一句话」** ——
输入是**已经跑完的 `run.boundary`**，输出是**报告**。
而折算说明的输入是**还没保存的草稿 + 全局档位**，输出是**表单里的预告**。
两者只是共用「notes → 人话」这个词，**数据来源与生命周期都不同**：
一个读**历史**（跑完了、不可变），一个算**预测**（还没跑、会变）。
塞进同一个模块，会让 `watch-report-core.js` 从「报告内核」变成「报告 + 预览内核」
—— **那正是这个项目一直在防的「一份文件管两件事」。**

**如果将来要补，我的建议**：**先不建文件**，把那个纯函数 `effectiveLineText`
**放在 `WatchRulesField` 上方的同文件位置**（`app.js:69030` 附近，紧挨它唯一的消费者），
**等出现第二个消费者时再抽出去**。这与 `watch-report-core.js` 当初被抽出来的理由
不矛盾 —— 它被抽出来是为了**写单测**（`tests/unit/watch-report.test.mjs`），
**单测才是抽文件的正当理由，不是「别人都这么放」。**

### 10.5 一句话回答

**不补。** 主通道（禁用 + 「不生效」徽标）已经守住，「能碰到却静默折算」的最危险形态
本轮不存在；折算说明是提案自己认定的兜底层，补它要凭空造第二份判定或改跨进程契约，
代价与收益不成比例。**如实记成已知缺口，并在 `app.js:69043` 那段注释后补一句
「本层（第二层：就地折算说明）未实现，见 §10」**，让下一个人读代码时不会以为它做完了。
**同时保留 `.watch-warn`，但把文案从「复述结论」改成「指出去路」** ——
那是全屏唯一缺的东西，也是提案点名必写的那半句。
