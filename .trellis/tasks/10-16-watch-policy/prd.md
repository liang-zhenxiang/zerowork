# PRD:「值守」—— 给无人值守的自动化任务一套可声明的规矩

## 背景(为什么做)

「自动化」这一页今天能表达的是**三件事**:提示词、时间、开关
(`docs/USAGE.md` §自动化)。到点之后 daemon 起一个会话、跑提示词、把运行记录落盘。

问题出在**这个会话跑起来之后**:

- 它**没有人在场**。`session-files.js:1066` 的 `buildRunExtensions()` 把整个 run 会话
  的权限门**硬编码成 `unattended: true`** —— `permissions.js:114` 的
  `willAskUser()` 直接 `return false`,审批类操作**一律自动拒绝**。
- 拒绝是**对的**(宁可拒绝,也不静默降级),但它是**一刀切的**:
  用户**没有地方**说「这个任务允许跑到 09:00 之前」「这个任务只准读,一个字都不许写」
  「这个任务可以往 `reports/` 里写,别的地方不行」。
- 于是用户面对的真实选择只有两个:**要么把权限档整体切到 `danger-full-access`**
  (整个应用跟着放宽,不只是这一个任务),**要么这个任务什么也干不了**。
- 而那半小时里**到底发生了什么**,用户回来只能翻「统计」的台账看一行
  `成功 / 失败` —— `success: false` 时那条 `error` 字段常常是一句
  `无人值守会话不应发起审批` 这种**从工具层抛出来的内部话术**,用户读不懂,
  也不知道**该怎么改**。

> 一句话:今天「自动化」能定的只有**什么时候跑**,
> 不能定**跑起来之后准许它做到什么程度**,也说不清**它为什么没干成**。

这一轮要补的正是这两格,而且**只补这两格** —— 不碰沙箱、不放宽任何默认档位。

### 与既有能力的关系(不重复造轮子)

| 已有能力 | 它管什么 | 本功能与它的分工 |
| --- | --- | --- |
| 权限三档(`read-only` / `workspace-write` / `danger-full-access`) | **全局**、**整个应用**的口径 | 本功能是**单个定时任务**的口径,且**只能更严、不能更宽** |
| 工作空间边界 | Agent 读写文件的**目录范围** | 本功能在**目录之内**再划一层「这个任务只准碰这些路径」 |
| 自动化运行台账(`appendRun`) | 记**成没成** | 本功能把**为什么**、**卡在哪一步**、**越了哪条界**写清楚 |
| 审计日志 | 逐条事件 | 本功能给的是**这次运行**的**一份可读报告**(审计仍是逐条的流水) |
| 会话「重新开始」/ 文件历史 | 回退**对话** / 回退**文件** | 本功能管的是**还没发生时**的边界,不是事后的回退 |

### 竞品核对(2026-10-16 检索)

- GitHub Actions / GitLab CI 的姿态是**声明式边界**:`permissions:`、
  `timeout-minutes:`、`concurrency:` —— 「这次运行准许做什么」写在工作流定义里,
  而不是靠一个全局开关。**「给一次无人值守的运行声明边界」是被验证过的形态。**
- Claude Code 的 `settings.json` 有 `permissions.allow` / `deny` 与 hooks,但它是
  **全局配置**,不区分「这一次运行」;Cursor 的 Rules 同理。
- 同类**本地 AI 桌面端**(Cherry Studio / Chatbox / LobeChat / Msty / AnythingLLM)里,
  定时任务普遍只到「提示词 + 时间」为止,**没有一家的定时任务能声明单次运行的边界**。
- 我们的**融合点**不是照抄 CI 的 `permissions:` 语法,而是把它接到本项目已有的身份上:
  边界**只能收紧**(与「宁可拒绝,也不静默降级」同源)、**越界即停并留证人**
  (与我们已有的审计纪律同源)、报告**说清下一步怎么办**(与「错误要可诊断」同源)。

## 期望(做什么)

### 1. 声明:每个定时任务多一份「值守规矩」

在「自动化」的编辑面板里,任务三要素之下新增一组**可选**的规矩(不填 = 今天的行为,
一个字都不变):

| 规矩 | 取值 | 不填时 |
| --- | --- | --- |
| **时限** | 分钟数(如 30) | 产品的 30 分钟内置保护(与今天一致) |
| **能力** | `只读` / `可写` / `跟随全局` | 跟随全局(与今天一致) |
| **可写范围** | 一个或多个工作区内的子路径(`reports/`、`data/out/`) | 整个工作目录 |
| **越界即停** | 开关,默认**开** | —— |

**三条硬约束(写死在模型层,不是靠界面自觉):**

- **规矩只能更严,不能更宽。** 「能力 = 可写」而全局是 `read-only` 时,
  这条规矩**不生效**,并在界面上**明说**「当前全局档位更严,本任务的『可写』不会放宽它」——
  参数被接受却不生效必须告警,静默失效比报错更危险
- **`danger-full-access` 下时限与可写范围照常生效** —— 它收紧的是**这个任务**,
  不是全局
- **绝不放宽任何默认档位。** 本功能**没有**任何一条路径能把权限档往上调;
  `unattended` 的既有语义(审批一律拒绝)原样保留,本功能只在**拒绝之前**
  多一层「这个任务自己声明的边界」

### 2. 执行:到点之后,规矩真的管用

`AutomationScheduler` 的 `enqueue` 增加**两个准时约束**,都由既有机制落地:

- **不并发**:同一个任务已在跑/在排队时不重复入队(今天 `isBusy` 已经这么做,
  本轮把它**写进规矩的语义**并补测试钉住)
- **时限**:运行开始后计时,到点**发 abort**(走既有的 `session.abort` 通道),
  并把这次运行标成**「超时中止」**——不是「失败」,两者要可辨

**越界即停**:run 会话的工具层在**既有**的权限判定之前,先过一遍**本任务声明的边界**
(`watch-policy.js` 的 `evaluateWatchBoundary`)。
越界时**拒绝该次调用并把理由回给模型**(与 `unattended` 的既有做法一致 ——
模型知道被拒了会换路子),同时在运行报告里记一条**越界证人**。

**「越界即停」这个开关管的是同一件事的下一步**(判据唯一,只在
`watch-policy.js` 的 `onExceedAction` 里回答一次):

| 取值 | 越界之后 |
| --- | --- |
| **开**(缺省) | 拒掉这次调用**并且把整轮叫停** —— 走既有的 abort 通道(与时限同一个出口)。定时任务没人看着,放它继续跑只会产出更多越界动作 |
| **关** | **只拒这一次调用**,模型收到理由后可以换个路子把活干完;整轮照常跑完,报告里记 `exceeded` |

> 关掉时报告状态是 **`exceeded`**(跑完了、但越了界);打开时是
> **`stopped`**(被规矩叫停)。两者都**不是 `failed`** —— 规矩按设计生效了,
> 不是功能坏了。`summarizeRun` 把这条顺序钉死:超时 → 越界停 → 失败 → 越界 → 好。

### 3. 交差:一份读得懂的报告

`appendRun` 的记录**新增字段**(只增不改,老记录照常可读):

```
boundary: { exceeded: Array<{ at, tool, detail }>, timedOut: boolean,
            stoppedByBoundary: boolean, readOnlyEnforced: boolean,
            scoped: string[], notes: string[], overflow?: number }
```

「自动化」的运行记录里,每次运行可以展开成一份**交差报告**:

- **结论一句话**:「跑完了」「跑完了但越了 2 次界」「到 30 分钟被叫停」「没跑起来」
- **它做了什么**:这次运行交付的产物、改过的文件(接既有 `versions` 与资料库数据)
- **卡在哪**:失败时的**人话解释** + **下一步怎么办**
  (如「这个任务要写文件,但当前全局档位是『只读』——把任务的『能力』改成
  『可写』,或把全局档位放宽到『只能改工作区』」)
- **越界证人**:哪一步、想做什么、被哪条规矩拦下

### 4. 视觉

- 规矩编辑区收进「自动化」既有的编辑面板,**不新开页面**(遵守 `docs/DESIGN.md` §3.9 盒子预算)
- 运行记录行从「一行结果」变成**可展开的交差报告**;**默认折叠**,不占开场视线
- 三态齐备(加载 / 空 / 错误);`boundary` 缺失的**老记录**照常显示,
  报告里如实说「这条运行早于『值守』功能,没有边界记录」——不编一个空的出来
- 视觉方案由 UI/UX 设计师 subagent 出稿(任务 `research/ux-proposal.md`)

## 非目标(本轮不做)

- **不做新的权限档位**,**不放宽任何默认值**(红线 4)。本功能只有「更严」这一个方向
- **不做跨任务的全局策略中心** —— 规矩跟着任务走,一个任务一份
- **不做「任务跑的时候实时插话」** —— 无人值守就是无人值守;要看着它跑就用「手动运行一次」
- **不改沙箱**,**不改 `unattended` 的既有语义**(审批仍一律拒绝;本功能只是在拒绝之前
  多一层任务自己的边界)
- **不做规矩的可视化调试器 / 模拟器** —— 规矩在运行报告里如实交代即可
- **不做定时任务的依赖编排**(A 跑完再跑 B)—— 那是另一个功能

## 难度

中偏难。daemon / 契约 / 渲染三层都有改动,且**「只能更严」这条不变量要在三层各钉一次**
(模型层拒绝构造宽度、执行层收敛、界面层如实告警)。风险集中在三处,均有明确对策:
与 `unattended` 既有语义的边界(对策:只加前置判定、不改既有分支)、
时限中止与既有 abort 的复用(对策:走同一条通道、只新增一个中止原因)、
老记录的向后兼容(对策:只增字段 + 缺字段的兜底文案有单测)。
