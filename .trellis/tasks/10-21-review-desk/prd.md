# 变更审阅台：把 Agent 改过的文件变成可审阅、可还原的队列

> 本轮方向由维护者调研后自选。竞品检索（Cherry Studio / ChatBox / LM Studio /
> Claude Desktop 一类）普遍只有「对话 + 产物列表」，**没有一个把「AI 改了我的文件，
> 我审过了吗」做成一条可走完的流程**。本项目已经有「文件时光机」（按文件的版本时间轴
> + 单版本预览 + 还原），缺的是按**变更**组织的审阅队列与并排对照。

## 背景

Agent 在办公场景里最危险的的动作不是「说错话」，而是**直接改用户的文件**。项目已经
为此留了后路（`versions/` 存每一版旧内容、可一键还原），但入口是「文件历史」：

- 它**按文件**组织：同一个文件今天被改了 5 次，你看到的是 5 个版本节点，不是「5 次改动」
- 它**没有审阅状态**：无法回答「这些改动我确认过没有」
- 它**只有单版本预览**：要判断「改了什么」，得自己在两个版本之间来回切换

用户真实的心理是：「AI 昨晚改了我的周报，我得看一眼，但我不想逐版翻。」

## 期望（用户可见）

新增侧栏页 **「变更审阅」**（排在「文件历史」旁）：

1. **按变更列队**：每个文件最近一次被覆盖 = 一条变更卡，显示
   文件 · 目录 · 时间 · 来源会话/工具 · `+N −M` · **待审阅 / 已审阅**
2. **并排对照**：选中一条，右侧给出「改前 / 现在」并排 diff（统一 diff 行着色），
   不再需要自己切版本
3. **审阅闭环**：
   - 「标记已阅」→ 该版本 id 被记为已阅；文件**再被改**会自动回到待审阅
   - 「还原到改前」→ 复用 `versions:restore` 的既有语义（先留当前内容、再写回）
   - 「回到那次会话」→ 跳回产生这次改动的会话
4. **计数与筛选**：顶部「待审阅 N · 已审阅 M」，可切「全部 / 待审阅」；
   侧栏条目带待审阅数量角标（0 时隐藏）
5. **空态/错误态/加载态**三态齐全（DESIGN §4），空态说清「还没有需要审阅的变更」

## 非目标

- 不做逐 hunk 接受/拒绝（版本存储是整文件快照，逐 hunk 会伪造出存不下的中间态）
- 不覆盖命令改的文件（`bash` 改的没有旧内容可留，与文件时光机的既有边界一致，界面要如实说明）

## 约束

- **只读 + 显式动作**：页面打开不得修改任何文件；「还原」必须先确认
- **如实**：超出扫描上限、二进制/超大文件跳过、当前文件已不存在 —— 都要在界面上说出来，
  不静默截断、不假装有 diff
- 复用既有版本存储与 `buildHunks`，不新造一套 diff
- 不做破坏性迁移：审阅状态单独一个小文件，坏文件当空（与 pin/projects 同口径）

## 验收标准

- [ ] 单测：审阅状态的读写/坏文件容错、`reviewed` 判定（版本 id 变化即回到待审阅）、
      列表排序与筛选、跳过项计数
- [ ] e2e（真实启动 Electron + 截图）：种子写入 → 页面出现变更卡 → 打开并排 diff →
      标记已阅 → 重启后仍为已阅 → 再改文件后自动回到待审阅
- [ ] 还原动作在 e2e 里断言**磁盘字节**真的退回（不看 toast）
- [ ] `npm run test` / `npm run test:gui` / `npm run lint:all` 全绿
- [ ] 截图经独立 UI/UX 设计师 subagent 评审并按其意见迭代

## 难度

中。daemon 侧只新增一个聚合读取 + 一个小状态文件；风险在渲染层页面与 diff 展示的
视觉质量，以及「当前文件内容」读取的安全边界（大小上限、二进制、文件消失）。

## 实施中修订：入口从侧栏移到「文件历史」页头

原计划把「变更审阅」作为独立侧栏项。全量 GUI 测试抓到一个**真实回归**：
`tests/e2e/session-pin.mjs` ⑬ 在 600px 高的窗口里断言任务行 ⋯ 菜单的「置顶」项
完整落在可视区内 —— 多一行 nav 之后它被推出约 8px，用例变红。临时移除该侧栏项后
13/13 恢复，归因确定。

**处置**：不新增侧栏项，也不放宽那条断言（它守的是真实可达性）。
待审阅数做成「文件历史」nav 项的角标；入口放在文件历史页头（「变更审阅 N」）。
两页本来就是同一份版本存储的两种看法，退回去也回到文件历史而不是首页。
e2e 已同步为「侧栏文件历史 → 页头变更审阅」。
