# 设计：命令面板的记忆

## 1. 数据形状

```js
{
  favorites: ["action:stats", "session:2026-10-03T...", ...],   // 有序，先收藏的在前
  usage: { "action:stats": { score: 2.5, lastAt: 1759500000000 }, ... }
}
```

- **为什么不是 `count` + `lastAt`**：那样每次读取都要按 `now - lastAt` 现算，
  读取侧就不再是纯查表；而且「衰减」会同时依赖读取时刻 —— 同一个文件在两台机器上
  读出的排序不同。存**已经衰减好的分数**，写的时候清算，读的时候只比大小。
- **为什么分数能自己衰减**：每次写入时先给**全部**旧分数乘一次衰减因子
  `2 ** (-elapsed / HALF_LIFE)`，再给这一次 +1。半衰期 7 天：一周不用，分数减半。
  于是「上周天天用、这周没用」会让位给「今天刚用过两次」。
- **上限**：`FAVORITES_MAX = 20`、`USAGE_MAX = 200`，超了按分数淘汰最低的。
  这不是性能问题，是**文件不能无限长**的问题（preferences.json 每次写是整体重写）。

## 2. id 的稳定性（这套设计的前提）

frecency 与收藏都靠 id 认条目，所以 id 必须**跨会话稳定**：

| 条目 | id | 稳定吗 |
| --- | --- | --- |
| 动作 | `action:new-task` 等（声明式动作表里写死） | ✅ |
| 设置分组 | `settings:<page.id>` | ✅ |
| 会话 | 会话 id | ✅（重命名不改 id） |
| 工作空间 | 路径 | ✅ |
| 专家 / 技能 | 名字 | ✅（改名即视为新条目，可接受） |
| 连接器 / 自动化 | 配置里的 id | ✅ |

**不做**「id 存在性清理」，理由与「会话置顶」同一条纪律（`CHANGELOG` 的置顶条目）：
会话文件可能只是暂时不在（移动、外置盘、同步中），那时抹掉用户的选择才是真的丢东西。
清理策略只有一条：**规模淘汰**（§1 的上限）。悬空的 id 永远只是「查不到对应条目，
所以不渲染」，不影响任何别的条目。

## 3. 排序位置（这轮唯一的判断题）

### 有查询时：匹配质量永远优先

```
matchRank ↑ → kindWeight ↑ → 常用分 ↓ → 原索引 ↑
```

新增的只是**第三级到第四级之间**插进去的一级。为什么必须在权重之后、原索引之前：
- 放在 rank 之前 = 「我打字了它还拿历史压我」，Raycast 手册与 Obsidian 的做法都明确否掉；
- 放在原索引之后 = 等于没有 —— 同分同类的条目本来就按原顺序排。

不传 `scoreOf` 时这一级恒为 0，**行为与改动前逐字节一致**，有一条回归锁守着。

### 空查询时：收藏 → 常用 → 其余

```
收藏（按收藏顺序） → 同组内按常用分降序（稳定） → 原顺序
```

**收藏用独立的伪分组置顶**，而不是「混进各 kind 组里排前面」：
结果列表是按 kind 分组渲染的（`paletteGroups`，组序 = 最佳 rank → KIND_WEIGHT），
空查询下 rank 全为 null，组序退化成纯类别权重 —— **动作组永远在最上**。
所以「把收藏的会话排到它所在组的最前」在视觉上等于没置顶（它还在动作组下面）。
用一个空查询专属的「收藏」组表达置顶，才配得上「置顶」这个词。

代价：收藏组里会出现跨类别的条目（一个动作、一个会话、一个技能并排）。
这是**有意的** —— 收藏本来就是「用户自己的短名单」，不是分类视图。
组内按收藏顺序（用户自己排的时间序），不按类别。

## 4. 交互

| 动作 | 键 / 鼠标 |
| --- | --- |
| 切换收藏 | ⌘D / Ctrl+D（browsers 的「加书签」同键位），或点行尾的星标 |
| 打开条目 | Enter（不变） |
| 选择 | ↑↓（不变） |
| 关闭 | Esc（不变） |

- **⌘D 而不是 ⌘F**：⌘F 在浏览器里是「查找」，在这个面板里没有别的语义冲突，
  但 ⌘D 与「收藏/书签」的既有肌肉记忆一致。
- **星标既显示也点击**：`<button>` 嵌在 `<button>` 是非法的 HTML，所以行本身仍是
  button，星标是**行内的 span**，点击路径由行的 `onMouseDown` 分派 ——
  `favorited && 命中 .palette-star` 时切换收藏、否则执行该条目。这样不必嵌套交互
  元素，键盘路径（⌘D）与鼠标路径（点星标）表达同一件事。
- **这个 `favorited &&` 前置判断就是「防误触」的全部**，没有配合 CSS 的
  `pointer-events: none`（那是 §7.9 给**独立按钮**的规则，这里结构不同）：未收藏的
  行上点星标那一格 = 点行，不会变成收藏陷阱。反向验证过 —— 去掉这个前置判断，
  点未收藏行的星标会把 ①条目误加收藏 ②面板不关（`tests/e2e/palette-memory.mjs` 的⑥）。
  加上 `pointer-events: none` 则会让 `.palette-star:hover` 永远不触发、白丢悬停反馈，
  而点击行为毫无变化（实测等价），所以不加。DESIGN.md §7.9 记了这条例外。
- **星标落在固定的一列**：名字 `flex: 1`（只作用于 `.command-palette`），星标因此
  行行对齐，而不是紧贴名字、随名字长短左右浮动。
- **非颜色的标记**（DESIGN §7.6）：实心星形（与未收藏的「没有星」是形状差异）
  + `sr-only` 文本「已收藏」（屏读）+ `title`（悬停）。
- 底部提示增加「⌘D 收藏」——提示里写了哪个键，哪个键就真的能按（既有纪律）。

## 5. 持久化路径

| 层 | 做什么 |
| --- | --- |
| `src/shared/ipc.js` | 登记 `settings:get-palette-memory` / `settings:set-palette-memory` |
| `src/preload/index.js` | 暴露 `getPaletteMemory()` / `setPaletteMemory(memory)` |
| `src/main/index.js` | 什么都不用做（不在 MAIN_HANDLED 里 → 自动走批量转发到 daemon） |
| `src/main/daemon/session-files.js` | 两枚 handler：读回（缺省空记忆）/ 校验后读改写落盘 |
| `src/main/daemon/preferences.js` | `readPaletteMemory(value)` —— **读写共用的一份判据** |

读侧丢弃、写侧抛错（照 `isThemePreference` 的口径）：写侧拒绝非法值是为了让
「写进去的东西一定能读回来」，读侧丢弃是为了让手改坏的 preferences.json
只影响面板记忆、不会让整个偏好读取失败。

## 6. 渲染层接线

```
App()
 ├─ paletteMemory state（**挂载时** getPaletteMemory() 预取，失败 → 空记忆 + 打开面板时重试）
 ├─ paletteEntries（不变，全集）
 ├─ paletteIdleEntries = orderIdle(actions + 最近5条会话, memory) + 收藏条目
 ├─ <CommandPalette memory onToggleFavorite onPick />
 └─ onPick / onToggleFavorite → setState + 异步写回（失败只记一条 warn，不打断）
```

- **写回是 fire-and-forget**：面板记忆是**体验增强**，不是数据。写失败不回滚界面、
  不弹错误（下次写入会带上当前状态）。这一条写进代码注释，免得后来者「补」成
  阻塞式 await。
- 读回失败（文件损坏 / 通道异常）→ 空记忆，面板照常工作。
- **只在首次打开面板时读一次**，不做「每次打开都读」：写回是异步的，读-改-写之间
  没有锁，每次打开都读就可能读到上一次写入尚未落盘的旧值，把用户刚收藏的那条「变没」。

## 7. 空查询在「没有收藏、没有使用记录」时与现状一致

干净配置（首次安装）下 `orderIdle` 必须**原样返回**调用方给的顺序 ——
新功能不能给老用户的首屏加噪声。有一条单测 + 一条 e2e 断言守着。

## 8. 首版不做（不要重新论证）

| 项 | 为什么 |
| --- | --- |
| 搜索时给收藏加权 | AC 的排序链里没有它；收藏在搜索时仍有星标可辨 |
| Reset Ranking 按钮 | Raycast 有，但我们的数据量级不需要；真要清就删 preferences.json 的一个键 |
| 收藏的拖拽排序 | 收藏顺序 = 收藏时间序，够用；拖拽要引入新交互范式 |
| 面板外的 frecency | 首页「最近会话」与侧栏顺序是另一套心智模型，混用会让「最近」不再可预测 |
| 跨设备同步 | 本项目是本地优先 |
