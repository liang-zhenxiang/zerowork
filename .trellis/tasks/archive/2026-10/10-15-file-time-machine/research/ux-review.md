# 独立评审：文件时光机（「文件历史」页）

> 评审人：资深 UI/UX（独立评审，非方案作者）
> 复核对象：`artifacts/file-history/` 六张真机截图、`src/renderer/src/app.css` 的 `.fh-` 段、
> `src/renderer/src/app.js` 的 `FileHistoryView`、`src/renderer/src/file-history-core.js`、
> `docs/DESIGN.md`
> 方法：逐张看图 + 逐像素采样（亮/暗两主题取同一行文字实测对比度）+ 读实现。
> 下文所有「实测」都是把 PNG 放大后直接取像素值算 WCAG 对比度，不是目测。

---

## 1. 结论

1. **基准态可以发**：`file-history-list-light.png` 的版面重心、盒子预算（全页只有一个
   内容卡）、时间轴形态与选中双通道、暗色层次都成立，与 `LibraryView` / `StatsView`
   是同一套语言，没有发现遮挡、重叠、出框。
2. **但有两处不能直接发**，都集中在「边界与反馈」：`broken` 行的说明文字被行级不透明度
   压到 **1.96:1（亮）/ 2.75:1（暗）**，是全页唯一读不出来的字；还原成功后预览当场切到
   「还原快照」，屏幕显示的正是刚被覆盖掉的旧内容，与 toast「已还原到 …」互相打架。
3. 两处都是小改动（换一个 token、少选一次），修完即可发；其余是打磨项，不阻塞。
4. 另有一条与方案稿的分歧（`+X −Y` 不上状态色）我判**实现是对的**，但注释需要改，
   见 §6.1。

## 2. 必须改（P0）

### P0-1　`broken` 节点的说明行读不出来（亮 1.96:1 / 暗 2.75:1）

**现象（可复核）**

- `file-history-broken-light.png` 第 1 个节点的三行文字（`10-15 16:22` /
  `内容已不在，这一版不能还原` / `刚刚`）与右侧来源行整片发白。在设备像素
  y≈397–465、x≈1290–1780 处实测：最深像素 `(185,185,185)`，对白底 **1.96:1**。
- 同图非 broken 节点（选中行）的同一行（y≈556–624）最深像素 `(123,123,123)`，
  对 `#f7f7f7` 底 **3.95:1**（未选中行对白底是 `(127,127,127)` / **4.00:1**）
  —— 同一个「次文」档位，broken 行只有它的一半。
- `file-history-dark.png` 同一行（y≈400–480）：最亮像素 `(97,97,98)`，对
  `#1c1c1e` 底 **2.75:1**；非 broken 节点同行为 `(153,153,154)`，**5.98:1**。

**为什么是问题**

- 数值不是巧合，是两次降档相乘：`.fh-node.broken, .fh-node:disabled { opacity: 0.55 }`
  （`src/renderer/src/app.css:12388`）叠在 `--text-secondary`
  （亮 `rgba(0,0,0,.5)`、暗 `rgba(255,255,255,.55)`）上 —— 亮色 `0.5×0.55 = 0.275`
  黑 = `(185,185,185)`，与实测逐位吻合；暗色是 `0.55×0.55` 白，同理。
- 这一行是「边界情形一律不许静默」的落点：**不能还原的原因**。形态通道（空心点 +
  整行淡出）确实成立，但用户读到的是「这里有一版用不了」，读不出**为什么**。
- 同一形态在本仓库已有判例：`docs/DESIGN.md` §2.1 记着 2026-10-01 那次回退 ——
  `--text-faint`(30%) 让图标淡到几乎看不见、读起来像一半图标没加载出来。
  这里是同一件事，只是淡的是句子而不是图标。

**具体怎么改（二选一，都是换 token，不新造档位）**

1. **首选**：只把 broken 节点的变化行（`versionChangeText` 返回的那句，渲染在
   `.fh-node-change`）提到 `color: var(--text)`，行级 `opacity: .55` 保留。
   这条路已被同图自己验证：该行的时间戳（`--text` 走 0.55）实测就是
   亮 `(115,115,115)` = **4.74:1**、暗 `(143,143,144)` = **5.27:1**，都回到全站
   次文基准（3.95:1）之上；代价只是这一句比旁边的来源行更黑一点，而这正是它该有的分量。
2. 或者**去掉 broken 行的整行 `opacity`**，改由「空心点 + 那句文字 + `cursor: default`」
   承担禁用语义。§7.6 已经要求「位置、文字、形态各自都能独立表达」，淡出是与文字重复的
   第三条通道，去掉不丢信息。

不要只把 `opacity` 从 .55 提到 .8：`0.5×0.8 = 0.4` 黑 ≈ 2.9:1，仍在基准之下，等于没修。

### P0-2　还原成功后，预览与高亮跳到「还原快照」——屏幕上正是被覆盖掉的旧内容

**现象（可复核）**

- `file-history-confirm-light.png`：用户确认的是第 2 个节点，预览头
  `10-15 16:22 · 34 B · 只读`，正文 `第二版: VERSION-TWO`；确认句写的是
  「把「周报.md」还原到 10-15 16:22 的样子？」。
- `file-history-restored-light.png`（e2e 在点完「确认还原」后立刻截图，
  `tests/e2e/file-history.mjs:498`）：正文变成 `第三版: VERSION-THREE`，高亮行是末尾
  那条 `restore · 把周报.md 改三次，每次换一版内容`，同一屏顶部的 toast 写着
  「已还原到 10-15 16:22」。
- 末尾那条正是**还原之前**的内容（`file-history-core.js:38` 的方向说明原文：
  「每一版都是某次改动之前的内容；当前磁盘上的内容不在其中」）。

**为什么是问题**

- 用户刚被告知「已还原到」，画面主体却正好显示着被覆盖掉的旧字节；最直接的两个结论是
  「没还原成功」或「还原到别的版本去了」。这一页没有任何东西能证明磁盘现在是第二版。
- 成因是实现细节：还原成功后 `refresh()`（`app.js:68135`）→ `reloadToken` 变化 →
  选中 effect 先 `setSelectedId(void 0)`（`app.js:68046`），再用 `defaultVersionIndex`
  选末位（`app.js:68060` / `file-history-core.js:73`）。「打开页面时落在最新一版」是好默认，
  「刷新后也落在最新一版」就不是了 —— 刷新后的最新一版不是磁盘状态。

**具体怎么改**

- 把「重拉详情」与「重选版本」拆开：`selectedKey` 变了才选末位；仅仅 `reloadToken`
  变化时，若原 `selectedId` 仍在新 `versions` 里就保留它。
- 保留的结果恰好是最好的成功证据：用户选的那一版，正文此刻就**等于**磁盘内容。
  末尾那条「还能退回来」的快照仍然在列表里可见，信息一点没少。

## 3. 建议改（P1）

### P1-1　预览体的 `max-height` 没生效（被 `.code-block pre` 的特异性顶掉）

- **现象/依据**：预览正文是 `<pre class="fh-preview-body">`，落在 `.code-block` 里
  （`app.js:68331`）。`.fh-preview-body { max-height: min(50vh, 420px) }`
  （`app.css:12509`，特异性 0-1-0）对不上 `.code-block pre { max-height: 60vh }`
  （`app.css:4759`，特异性 0-1-1），**后者赢**，与书写顺序无关。
- **为什么是问题**：方案 §3.7 把限高写死为 `min(50vh, 420px)`。窗口高 1200 CSS px 时，
  1 MiB 的版本会把预览撑到 720px（设计值只有 420），多出的 300px 把方向说明与卡片底
  挤出首屏。现在看不出来，只因为 fixture 那一版是 36 B。
- **怎么改**：把选择器提到同一层级或更高，例如 `.fh-preview pre` /
  `.code-block .fh-preview-body`；改完在 `tests/e2e/file-history.mjs` 里断言 computed
  `max-height`，否则下次还会静默失效。

### P1-2　时间轴主线在每一行之间断 12px

- **现象**：`file-history-list-light.png` 沿刻度槽列（设备像素 x=1241）竖向扫描：
  主线从 y=330 连续到 **y=428**，然后中断，下一段要到 **y=453** 才起 ——
  中间 24 设备像素（12 CSS px）是卡片底色。3 个节点时断点更多，20 版时会读成一串短横线。
- **依据**：每个 `.fh-node` 上下各有 `--space-2`(6px) 的 padding（`app.css:12360`），
  而竖线是绝对定位在 mark 槽里的 `top:0 / bottom:0`（`app.css:12400`），
  所以两行之间必然空出 `6+6`。既有的 `.fh-node.first/.last` 9px 裁切
  （`app.css:12410` / `:12414`）说明作者本意是**只在两端**裁掉、中间连起来。
- **为什么值得改**：「时间在流动」是这条线唯一的存在理由；断成虚线，时间轴这个主角
  就少了一根骨头。这也是全页唯一一处「设计意图与渲染结果不一致」的可见形态。
- **怎么改**：让伪元素跨过行内 padding，例如 top/bottom 取
  `calc(-1 * var(--space-2))`，并确保 `.fh-node-mark` 不裁剪（`overflow: visible`）。

### P1-3　同一分钟内的多个版本，时间轴上无法区分

- **现象**：`file-history-dark.png` / `file-history-restored-light.png` /
  `file-history-narrow.png` / `file-history-broken-light.png` 四张图里，2–3 个节点的
  身份行**全是** `10-15 16:22`、注脚行**全是**「刚刚」；同一屏没有任何字段能分开它们
  （只有右侧 `write` / `restore` 与变化行不同）。
- **依据**：`formatVersionTime` 只有分钟精度（`file-history-core.js:46`），而且节点身份行、
  预览头、确认句、成功 toast 共用这一个格式（同文件 `:174` / `:180`）；
  `formatRelativeTime` 对 <60s 一律「刚刚」（`:55`）。
- **为什么是问题**：Agent 连写同一个文件多次是常态（这组 fixture 的会话就叫「改三次」）。
  那时「把「周报.md」还原到 10-15 16:22 的样子？」对应 2–3 行，用户在按下确认前
  **无法在这句话里定位**自己选的是哪一版 —— 而这正是二次确认的全部价值。
- **怎么改（最小）**：把 `formatVersionTime` 改成带秒的 `MM-DD HH:mm:ss`，四处同源、
  改一处即可，且不破坏「同一格式」。代价是每行多 3 个字符。

## 4. 可以不改（P2，附理由）

- **P2-1　左列目录行与右卡 meta 行逐字重复**（单文件时两边都是
  `T/zerowork-ws-file-history-1g0XnM`，见 `file-history-list-light.png`）。
  不改：多文件时它是区分同名文件的唯一线索，删了会在主用例上丢信息；重复只在单文件时出现，
  代价是两行同色小字。目录行取「末两段」（`file-history-core.js:99`）在临时目录下会
  露出 `T/…` 这种技术尾巴，属 fixture 现象，真实工作区下是「市场部/2026Q4」这种可读形态。
- **P2-2　窄窗丢掉「文件历史 · N 个文件」与目录行**
  （`.fh-index { display:none }`，`app.css:12563`；区头在 `.fh-index` 里，
  `app.js:68180`）。不改：picker 已经给出「当前文件 · N 版」，列表总数是可牺牲的次要信息；
  为了让计数留下而在 picker 那行再塞一枚数字，会把那一行变挤。
- **P2-3　未选中圆点与连接线都用 `--border`**，亮色下对白底实测 1.25:1
  （`(230,230,230)`），暗色下对 `#1c1c1e` 实测 1.44:1（`(56,56,57)`）。考虑过换
  `--text-faint`，不改：主线的语义是「位置 + 顺序」，形态（点 + 线）已经在承担；
  压深它会跟时间与正文抢注意力，而选中态另有圆点形态这条第二通道。
- **P2-4　`.fh-confirm` 与它上面的 `.code-block-head` 同为 `--bg-raised`**
  （竖扫 `file-history-confirm-light.png`：y664–717 与 y720–828 都是 `(247,247,247)`，
  中间只有 1px `--border`；`app.css:12524` vs `:4731`），确认条读起来像 header 的第二行。
  不改：换 `--bg-hover` 会改成与预览正文更近、更糊；header 的底边线已经把两段分开，
  确认句本身足够显眼，且 §3.7 要求次级面一律不带边框。
- **P2-5（代码推断，未能截图验证）　时间轴节点的全局焦点环会被滚动容器裁掉左右两段**：
  `.fh-timeline` 有 `overflow-y: auto` 且 `padding: 0`（`app.css:12350`），`.fh-node`
  撑满宽度（`:12360`），全局焦点环是 `outline: 2px + offset: 2px`（`:852`），
  于是左右两条竖边会落在裁剪区之外。我判**暂不改**：这一轮没有提供焦点态截图，无法证伪；
  且上下两条横边仍可见，焦点并非不可见。若后续要修，最小改动是给 `.fh-timeline`
  补 4px 左右内边距（或节点改用负 `outline-offset`）。
- **P2-6　`app.css:12205` 的注释引用了一个不存在的类名** `.home-recent-head`
  （全仓库只有这句注释与两份 research 提到它）。这是文档级小错，不影响观感；
  真正成立的对照是 `.proj-section-title`。`.fh-index-head` 复制了它的
  `font-size` / `color` 而不是复用类名（`:12206` vs `:9780`），我判可接受：
  两者结构不同（这里没有行内计数 span），且本页只有这一处。

## 5. 我核对过、判定没问题的

1. **盒子预算**：全页只有 `.fh-card` 一个内容卡；左列无边框、确认条无边框、预览是卡内
   内框工具（复用 `.code-block`）。`file-history-list-light.png` 里除卡片本体外没有第二个
   带边框的盒子。
2. **文字都在容器内，无遮挡/重叠**：右列来源行最右文字像素 x=2460，卡片内容右边界
   2473（差 13 设备像素 = 节点 6px 右内边距，正好贴齐不裁切）；左列注脚行最右 1134，
   行内容右界 1135，**未触发省略号**；窄窗（`file-history-narrow.png`）下时间轴与预览
   全宽落在卡内。六张图逐张看过，没有发现任何元素互相压字。
3. **层级**：卡头 13px/主文 → meta 12px/次文 → 时间轴时间 13px/主文 →
   变化行·来源·相对时间 12px/次文 → 预览正文 12px 等宽。同屏没有出现同档两义。
4. **暗色无亮片**：「还原到此版本」是 `.mini-btn`，实测填充 `#1c1c1e`，比它所在的
   头部 `#26262a` **更深**一圈，加 `--border` 描边，不是白片；预览体 `#2c2c2e`、
   卡片底 `#1c1c1e`，层次方向与亮色一致。
5. **暗色「选中 ≠ 未选中」**：选中行底 `#26262a` vs 卡片底 `#1c1c1e`（实测可辨）
   ＋ 圆点 12px 实心 `--text` vs 10px `--border`，双通道成立（`file-history-dark.png`
   第 3 个节点高亮、第 2 个不亮，肉眼可分）。说明：行底本身的比值确实很小
   （暗 1.12:1、亮 1.07:1），靠的是圆点形态第二通道 —— 这正是 §7.6 要求的形式。
6. **状态不只靠颜色**：broken = 空心点 + 文字 + 淡出；选中 = 行底 + 圆点大小/实心；
   `+1 −1` 带符号。没有一处只靠色相。
7. **键盘可达**：节点是真 `<button>` 装在 `<li role="listitem">` 里，天然进 Tab 序；
   broken 用 `aria-disabled` 而非 `disabled`，**仍可聚焦**（`app.js:68228`–`:68236`），
   点击直接 return 不误触发；`.fh-file-row` / `.fh-picker` 同为 button。
8. **还原不用危险色**：预览头右端是 `mini-btn`（`app.js:68307`），无 `danger` 类；
   `--danger` 只出现在还原失败的就地错误条（`app.css:12541`）。危险感与可逆性匹配。
9. **确认条说全了三件事**：放大看图能同时读到文件名「周报.md」、目标时间
   `10-15 16:22`、「现在的内容会先存成一条新版本…之后还能再退回来」；进入确认态后
   头部的触发按钮消失，没有出现两个还原按钮。
10. **三态互斥**：加载=骨架（`role="status"`，`app.js:68168`）、空=EmptyState、
    错误=ErrorState+重试；数据未到不渲染空态文案。
11. **窄窗退让**：`file-history-narrow.png` 左列收起、picker（`周报.md · 3 版 ▾`）替代，
    时间轴与预览全宽，无遮挡；picker 用的是既有 `.pop-menu` 语言，不是原生 select。
12. **一致性**：刷新键与 `StatsView` 同款（`IconRefresh` 13 + 「刷新」，`app.js:68351`
    vs `:67608`）；截断说明用既有 `.stat-hint`（同 `LibraryView`）；「文件已不在」
    措辞与 `ProjectView` 逐字一致。
13. **零新增动画 / 零新增 token**：时间轴无入场、连接线无生长、确认条无滑入，
    §10.3 无需登记；颜色全走 token（无字面量），
    `color-mix(in srgb, var(--text) 8%, transparent)` 是既有写法。
14. **窗口右缘那条 12 设备像素的 `#f2f2f2` 竖带**（`file-history-*.png` 的 x≥2548）
    在 `artifacts/library/*` 与 `artifacts/settings/*` 上同样存在，是窗口级既有现象，
    不是本页引入的，不计入评审。
15. **侧栏「文件历史」不显示当前页高亮**：与「诊断」「统计」一致（都是同一枚
    `.nav-item`，无 active 态），属既有导航习惯，不是本页的退步。

## 6. 与 `ux-proposal.md` / `docs/DESIGN.md` 冲突或需要裁决的地方

### 6.1 与 ux-proposal §3.3 冲突：`+X −Y` 没上状态色 —— 我判实现是对的

- 方案 §3.3 写「`+` 走 `var(--ok)`、`−` 走 `var(--danger)`（全站三处已同款）」，
  同时自己留了降级方案；实现用的是降级方案：`.fh-node-change` 整行 `--text-secondary`
  （`app.css:12481`，图里 `+1 −1` 与「被一次…替换」同色）。
- **判断依据**：`docs/DESIGN.md` §2.4「状态色只表状态」—— diff 行数不是状态。
  全站上色的两处（`app.css:5355/5363/5367` 的 `.tool-change`、`:6399/6403` 的
  `.changes-summary`）出现在「一次工具运行的结果」上下文里，与「历史里某一版被谁替换」
  不是同一件事；一屏 20 行红绿会让时间轴失去主角地位，而且 broken 行本来就占用了
  变化行这一格。**但这意味着方案 §9.1 表里「沿用既有 `.tool-change` 口径」那句要改。**
- 顺带：`app.css:12480` 的注释写「变化行走 `.tool-change` 的既有口径」，
  会让后来人以为颜色也对齐了。建议改成「同字体口径（等宽 + meta 档），颜色不借用
  状态色（§2.4）」。

### 6.2 与 ux-proposal §3.7 冲突：预览限高（见 P1-1）

方案把 `max-height: min(50vh, 420px)` 写死并要求「不留实现者自由发挥」，实际被
`.code-block pre` 的 `60vh` 以特异性顶掉。这是实现与方案的事实性不符，不是审美分歧。

### 6.3 与 `docs/DESIGN.md` §3.4 的关系：需要一条附则（见 P0-1）

§3.4「禁用行只改透明度，不置灰背景」被逐字遵守了，但「只改透明度」与 §2.1
「降到 `--text-faint` 是降两档，只在文字本身是唯一状态信号时才用」的精神相抵：
行级 `opacity` 是乘法，作用在已经降过一档的 `--text-secondary` 上会直接击穿基准
（实测 1.96:1）。建议在 §3.4 补一句：淡出不得把文字对比度压到次文基准以下；
若必须淡出，需要保读的那一句走 `--text`。

### 6.4 与 ux-proposal §11 验收第 6 条的关系：需要按实测放宽

「不出现亮片」成立；「不出现『选中与未选中同色』」这条卡在边界上 —— 实测选中行底与
卡片底只差 1.12:1（暗）/ 1.07:1（亮）。我判**可以接受**，因为 `--bg-raised` 是 §3.7
指定的「选中底」语义、全站选中都这么表达，而本页另有圆点形态这条第二通道（§7.6）。
验收断言建议只钉「圆点形态可断」，不要把「行底色差」写成硬阈值。

### 6.5 方案未覆盖、需要补一句的一处

§4.4 只说了「还原后时间轴末尾会多出一条、必须当场刷出来」，没有说刷新后选中落哪儿，
实现就落在了末位 —— 这正是 P0-2。建议方案补上「还原后选中保持在用户刚还原的那一版」，
否则下一位实现者会照着现状再写一次。
