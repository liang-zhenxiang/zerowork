# 首页上手清单的三态：视觉方案（#148）

Issue 要求先把视觉方案想清楚再动手，难点是**与 §3.9 盒子预算、§3.8 垂直节奏的关系**。
下面先摆约束，再给结论与理由。

## 一、现状为什么会坏

```js
if (error !== void 0 || snapshot === void 0 || workspaces === void 0 || sessions === void 0) return null;
```

一句 `return null` 把三件事压成了同一个画面 —— **什么都不显示**：

| 情形 | 现在 | 该有什么 |
| --- | --- | --- |
| 三个 IPC 还在路上 | 什么都不显示 | 可辨的等待形态 |
| 读失败（任一抛错） | 什么都不显示 | 就地错误 + 重试（§4） |
| 三步都完成且未展开 | 什么都不显示 | **只有这一种**该什么都不显示（现在是那枚小按钮） |

后果不是「少了一块 UI」，是**撒谎**：读失败的用户会读成「这个应用没有引导」。

## 二、约束（这两条决定了方案长什么样）

### §3.9 盒子预算：主列只允许一个内容卡

> 「首页主列就是输入卡：唯一的白底、唯一的 `--shadow-input`、唯一的渐变槽。其余元素要么是
> **填色无边的次级面**（上手清单），要么是**细边胶囊**（能力 chip），要么纯排版。」

所以**不能**把现成的 `.state-error` 直接搬进来 —— 它带 `1px solid var(--danger)` 边框与
危险色底。放进主列就是**页面上第二个盒子**，直接违反 §3.9；而且它外面再套一层清单的次级面，
会变成「卡里嵌卡」。

> 注：`.state-error` 在侧栏与设置弹层里是对的 —— 那里不是「一个页面一个盒子」的场景。
> §3.9 约束的是**首页主列**，不是整个应用。这一条要说清楚，免得后来者以为要全局去边框。

### §3.8 垂直节奏：清单槽的底距恒为 `--space-5`(16px)

> 「能力 chip → 上手清单 = `--space-6`(24)；上手清单 → 输入卡 = `--space-5`(16)，
> 必须 **> 清单内部行距（`--space-3`）**」

三态**共用同一个槽**，所以三态都必须落在 `.home-guide` 这个类上（它的
`margin-bottom: var(--space-5)` 就是那 16）—— 换形态不换槽，节奏自然不动。

## 三、结论

| 态 | 判据 | 形态 | 关键类 |
| --- | --- | --- | --- |
| **加载中** | 三份数据任一为 `undefined`，且无 error | `.home-guide` 次级面 + 3 条骨架行 + 1 条说明骨架行 | `.home-guide` + `.home-guide-row` + `Skeleton` |
| **读失败** | `error !== undefined` | 同一块次级面 + 一行：危险色图标 + 「读取失败：<原因>」 + `重试` | `.home-guide` + `.home-guide-row` |
| **三步完成** | `allDone && !expanded` | 不变：一枚「上手清单」小按钮 | `.context-row` |

**三态没有一个新盒子**：加载与错误都复用清单那块「填色无边」的次级面。错误的表达靠
**图标 + 危险色文字 + 重试按钮**，不靠边框 —— 这与全站「边框是内容卡的身份」一致。

## 四、两个刻意的判断（Issue 点名要想清楚的）

### 判断 ①：加载中给骨架，而不是留白

三条理由，缺一条我都会选留白：

1. **§4 已经定过调**：「结构已知的等待场景用骨架屏：骨架行与真行同尺寸、同类名，使列表到达时是
   『同一片区域被填上』，而不是整块替换」。清单的结构是已知的（固定三行 + 一句说明）。
2. **留白不是「安静」，是「跳动」**。今天就是留白：三个 IPC 在路上时那块不存在，数据到达后
   整块插进来，**输入卡被顶下去一次**。骨架与真行同高，跳变消失。
3. **它不是「闪一下再消失」**，因为骨架与真清单**同高同位**：肉眼看到的是灰条变成文字，
   不是一块东西出现又不见。Issue 担心的那种「会闪的东西」是**转圈/加载文案**——
   那类东西会在数据到达时整块消失、位置塌掉，本方案没有这个问题。

> 反向判断也记录在此：**不加延迟**（不做「150ms 后才显示骨架」）。侧栏「历史任务」骨架就是
> 立刻显示的既成先例，两处行为要一致；加一个延迟阈值会给这条最短路径引入一个定时器与一处
> 新的可配置常量，换来的只是「本地 IPC 那几毫秒不闪灰条」——不划算。

### 判断 ②：错误态不吞掉原因

保留 IPC 抛出的原文（`读取失败：<message>`），不替换成「操作失败」这类空话 ——
与项目「错误要可诊断」一致。重试就是 `load()` 本身（与侧栏 `ErrorState onRetry` 同一条路）。

**要不要加「重试中」形态？** 不加。重试会立刻把 error 清空 → 回到「加载中」的骨架，
用户看到的是「按下去、灰条回来了」，本身就是进度反馈；再叠一个局部 spinner 是重复表达。

### 判断 ③：错误原文照抄，不「美化」

真实失败时那段文案会长这样（截图里的注入版只是一个更短的例子）：

```
读取失败：Error invoking remote method 'settings:snapshot': Error: <daemon 的报错>
```

前半截是 Electron 的包装、技术上可以直接剥掉。**决定不剥**：

- 全站现在都是这么显示的（例如 `runtimes:reset` 的拒绝理由会原样进 toast），
  为首页单独发明一套清洗规则，会造成「同一个错在两处长得不一样」
- 那半截对**排查**有用（通道名就是出错的那一路）；剥掉之后真出问题时少一条线索
- 真要美化，应当是全站统一的一次改动（连同 toast / 侧栏 / 设置页），那是另一件事

用户读到的是「读取失败」四个字 + 一个重试按钮，这就够了；后面那段是给愿意追问的人看的。

## 五、对既有守卫的影响

| 守卫 | 影响 |
| --- | --- |
| `gui-smoke` 的「首页主列垂直节奏 = 12 / 12 / 24 / 16」 | **不受影响** —— 三态都用 `.home-guide`，`margin-bottom` 仍是 `--space-5`。这条断言在「骨架态」下也成立（同一类名） |
| `onboarding` 的「配好模型之前，清单不整块消失」 | **变得更强** —— 它此前要靠「.home-guide 或回头路按钮出现」来排除「IPC 还在路上」的假过（注释里写了这件事）；现在「还在路上」有自己的形态，歧义消失 |
| `check:theme-tokens` | 不新增颜色字面量：危险色用 `var(--danger)`，骨架用 `Skeleton` 既有的 `color-mix(--text 8%)` |
| 受控例外登记（§5） | 不新增过渡属性，无需登记 |

## 六、不做

- 不给错误态加边框（§3.9，理由见上）
- 不做「延迟显示骨架」（理由见判断 ①）
- 不动「三步完成」那枚小按钮（Issue 明确说保持现状）
- 不把 `.state-error` 全局去边框（它在前两处是对的）
