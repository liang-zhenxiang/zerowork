# 发布说明的 PR 清单取错了对比基准

## 背景（v0.4.0 发布时实测）

`release.yml` 的「生成变更清单」这一步用**上一个 tag 的创建时间**当分界点，
而「上一个 tag」是这么取的：

```bash
prev="$(git tag --sort=-v:refname | grep -v "^${TAG}$" | head -n 1)"
```

beta 渠道**每次合并 main 都会打一个 `vX.Y.Z-beta.N`**，于是在稳定版发布时，
`git tag --sort=-v:refname` 里排在 `v0.4.0` 之后（版本序更大）的正是
`v0.4.0-beta.16` —— 分界点落在**几小时前**，清单里只剩发布 PR 自己。

**实测证据**（v0.4.0 的 Release 页）：

| | 清单条数 | 完整变更链接 |
| --- | --- | --- |
| 发布流水线产出 | **1**（只有 #127 发布 PR） | `v0.4.0-beta.16...v0.4.0` |
| 修正后 | **51** | `v0.3.0...v0.4.0` |

后果不只是难看：**这一版实际合并了 51 条 PR，而 Release 页告诉读者只有 1 条**。
「本版合并的 PR」这个标题下的内容因此是**错的**，而且错得不像故障
（有一段像模像样的清单），不核对就发现不了。

## 修法

- **稳定版**（tag 不含 `-`）：候选取 `vX.Y.Z-*` 之外的 tag，即只跟上一个稳定版比。
- **预发布**：保持原样（与上一个 beta 比）—— beta 的读者要的正是「相对上一个 beta
  多了什么」。

## Acceptance Criteria

- [x] `release.yml` 的 prev 选取按发布类型分叉
- [x] 在**真实 tag 列表**上验证：`v0.4.0 → v0.3.0`、`v0.4.0-beta.16 → v0.4.0-beta.15`
      （老写法下 v0.4.0 会取到 beta.16）
- [x] 用**修正后的同一段逻辑**重新生成 v0.4.0 的发布说明并更新已发布的 Release
      （51 条 + 正确的对比链接）—— 这段逻辑因此在一份真实的发布数据上端到端跑通过
- [x] `actionlint`（CI 的「工作流静态检查」）通过

## 约束与已知限制

- **不能为它再打一个 tag 做端到端验证**（v0.4.0 已经发布，tag 不能移）。
  因此验证方式是：① CI 的 actionlint；② 用同一段逻辑在真实 tag 列表与真实
  GitHub API 上跑出 v0.4.0 的正确清单。这比「打一个 tag」弱一档，如实记在这里。
- 取「排除自己之后最大的那个」而不是「严格小于自己的最大者」：这一步只在当前 tag
  是最新 tag 时运行（发布即最新），少一层版本序比较也就少一处 `sort -V` 的可移植性风险。

## 难度

低（改 3 行），但**发现它需要真的盯着 Release 页看**。
