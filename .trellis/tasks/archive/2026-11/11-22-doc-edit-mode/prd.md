# PRD：修订模式——写入先生成待审建议（#456）

## 背景

`write` / `edit` 直接覆盖用户文件。事后审阅台只能看整文件 diff，「错了不能逐条回退、不知道改了哪几句」让用户不敢让 AI 直接改合同、周报。竞品 WorkBuddy 把 AI 修订做成「不覆盖原文、以修订建议呈现、接受后才写入」——本轮在**文件写入层**落地同样的纪律：修订模式下，Agent 的写入先变成待审建议。

本 Issue 只做底座：开关、拦截、建议存储与读取接口。逐条接受/拒绝 UI 在 #457，写回/版本/审计在 #458，e2e 与文档在 #459。

## 目标

1. **会话级开关**「修订模式」，默认关；状态随 `session_state.docEditMode` 下发。
2. 开启时，`write` / `edit` 对**工作区内文本文件**（`.md` / `.markdown` / `.txt`）不落盘，生成待审建议并 `block` 该次调用；模型收到可理解的原因（「已记录建议，等待用户接受，不要原样重试」）。
3. 建议含：目标绝对路径、基准内容 SHA-256、前后全文、结构化 hunk（含上下文）、来源会话、创建时间。
4. 持久化在配置目录 `doc-edits/`，跨重启可读；提供 list / read / delete 接口。
5. 非文本 / 工作区外 / 超大文件 / 无法应用（`oldText` 找不到）**明确拒绝并说明原因**，不静默退化成直接写。

## 非目标

- 不做接受/拒绝 UI（#457）、不做写回（#458）、不做 docx（#460 决策）。
- 不改变权限门与 hooks 的判定；修订拦截排在它们之后，只做「不落盘 + 留建议」。

## 约束

- 拦截必须排在权限门之后：权限/hook 拒绝是终局，被拒的调用不产生建议。
- 建议存储不 import Electron，可被 vitest 直测。
- 单文件 max 1 MiB；diff 规模沿用现有 `DIFF_CELL_BUDGET`，超限拒绝。
- 不新增依赖；不重排 app.js 大文件；中文内容不得有 U+FFFD。

## 验收标准

- [ ] 开关开启后，write/edit 成功回执但目标文件内容与 mtime 不变（哈希断言）
- [ ] 建议 JSON 含 path / baseSha256 / before / after / ops / hunks / sessionId / createdAt
- [ ] 非白名单扩展名、工作区外路径、超大文件、edit oldText 不匹配 → `{block:true}` 且原因可操作
- [ ] 权限门或 PreToolUse 拒绝时**不**产生建议
- [ ] 重启后 list/read 仍能拿到建议；delete 后消失
- [ ] 单测：白名单/路径、哈希、hunk 结构、存储往返、删除、超限拒绝
- [ ] 开关关闭时行为与现状完全一致（回归由 #459 的 e2e 覆盖）
