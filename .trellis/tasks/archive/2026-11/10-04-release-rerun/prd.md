# 发布说明可以手工重算（#129）

## 背景

v0.4.0 发布时发现 PR 清单取错了对比基准（稳定版取到了最后一个 beta tag）：清单里只有
**1 条**，而那一版实际合并了 **51 条**（根因与修法见 #128）。

修流水线只解决「下一次」，**这一份已经错了的说明改不回来**：

- `release.yml` 只有 `push: tags` 一个触发口；
- 重跑那次 workflow run 用的是 **tag 当时那个提交里的 release.yml**（旧版本），改不动说明；
- 唯一办法是维护者**现场手工** `gh release edit --notes-file`（v0.4.0 就是这么修的：
  本地用修正后的同一段逻辑重新生成清单，拼回正文再 edit）。

也就是说：**流水线的产物一旦出错，就没有可复用、可复核的修正路径**，只能靠人记住。
这与本项目「把记得住变成改错就红」的一贯做法相反。

## Requirements

- `workflow_dispatch`，必填输入 `tag`（已发布的 tag，形如 `v0.4.0`）。
- 与正常发布**共用同一段生成逻辑**（同三个 job），不许各写一份 ——
  「修好了一条路、另一条还错着」正是这次事故的形态。
- 只重算说明：**不构建、不重传安装包**（资产已经在 Release 上；重传会覆盖或报错，
  而它们本身没有问题）。
- 检出的 ref 用**输入里的 tag**，不是 main：说明的依据必须是**发布当时**的
  CHANGELOG 与 package.json（main 上可能已经有下一个版本的 `[Unreleased]`）。
- 输入必须真实存在：不存在时**第一步就报错退出**。
- 红线：`${{ }}` 一律经 `env:` 中转再进 `run:`。

## Acceptance Criteria

- [x] `workflow_dispatch` + 必填 `tag` 输入；`run-name` / 各 job 的 `TAG` 都取输入
- [x] `installers` job 与「附上安装包」步骤在 dispatch 下不跑
- [x] 检出的 ref 取输入 tag；新增「校验 tag 存在」步骤
- [x] **真跑验证**：合并后 dispatch `tag=v0.4.0` → run 成功、说明与修正后的一致
      （51 条 + `v0.3.0...v0.4.0`）
- [x] **反向验证**：dispatch `tag=v9.9.9`（不存在的 tag）→ **必须失败**且失败在
      「校验 tag 存在」这一步（证明输入真的被用上了）
- [x] `docs/MAINTAINER_GUIDE.md` 的发布一节写清这条路径与它的边界

## 约束

- 不动 tag（v0.4.0 已发布，tag 不能移）。
- 不改 beta 流水线（它有自己的触发与渠道守卫）。
- 发布说明的**内容组装顺序**（指引 → 摘要 → CHANGELOG → PR 清单）不变。

## 难度

低。成本主要在**验证**上：这条路径只能靠真的 dispatch 一次来证明。
