# 设计：把 delayMs 的断言从「测试进程墙钟」挪到「服务端发送时刻」

## 问题本质

现状断言测量的是 `fetch` 从开始到读完体的耗时，再相减。这个数字包含：

```
测试进程调度 + TCP 往返 + 服务端 setTimeout + GC + 其他 worker 抢 CPU
```

`delayMs` 只占其中一部分。全量并行（40 worker）时其余部分变大且**不可预测**，
250ms 的阈值就被吃穿 —— 而且**只会往一个方向坏**（测出来更接近 0），
所以它是假红，不是真缺陷。

## 为什么不能用「更稳的墙钟阈值」

三条路都试过（见 PRD 表格）：把阈值调低 / 改成测 span / 加大 delayMs，
本质都是给一个不可控的量留余量。余量留多少是猜的；负载再高一次就再红一次。
这是本项目已经写进规范的错误形态：**把「这台机器碰巧是什么样」写进断言**。

## 方案：服务端记录时刻

mock 本来就在服务端 `await sleep(delayMs)`，它**知道**自己什么时候发每一片。
把这个事实记下来，就得到一个不受测试进程负载影响的观测量：

```js
const sentAt = [];              // 每次 send() 记一个 performance.now()
const send = (delta, ...) => {
  sentAt.push({ at: performance.now(), delta });
  res.write(...);
};
```

断言建立在**服务端自己的时间轴**上：

| 断言 | 守什么 | 单调安全性 |
| --- | --- | --- |
| 开了 `delayMs` 时，相邻正文片间隔 `>= delayMs * 0.9` | `sleep` 真的发生在片之间 | 机器慢 → 间隔更大，不会假红 |
| 未开时，相邻正文片间隔 `< delayMs / 3` | 默认路径确实不等待 | 默认路径无 sleep，只受调度影响 |
| `delayMs` 那台的首个正文片，相对请求开始 < `delayMs / 2` | 第一片不等待 | 首片无 sleep |
| 网络层收到 ≥2 个非空 `delta.content` | 流式真的分片了（不是一次性写出） | 不涉及时间 |

注意：`performance.now()` 在服务端的 `sleep` 之后取，测的是**同一进程内的定时器实际延迟**。
Node 的定时器只会晚不会早，所以 `>= delayMs * 0.9` 是安全的（留 10% 给定时器精度，
`setTimeout(300)` 实测 300–303ms）。

## 为什么不测 `setTimeout` 之前的时刻

`delayMs` 的作用点就是那个 `await sleep()`。记录 `send` 前后时刻即可，不需要埋点进
`sleep` 内部 —— 埋点越多，mock 与真实流行为的偏离越大。

## 兼容性

- `sentAt` 是**纯增量**字段，既有 20 多个用例不读它，行为零变化。
- 默认 `delayMs = 0` 时不记录？不 —— 一直记录更简单，成本是每片一个对象，
  而 mock 每片本来就构造了 chunk 对象。保持记录，测试按需读。
- 不改变 SSE 字节：仍先发 role 片，再发正文片，最后 stop 片。

## 反向验证计划

1. 删掉 `if (index > 0 && delayMs > 0) await sleep(delayMs);` → 新断言必须红
2. 把 `delayMs` 改成只 sleep 一次而非每片之间 → 若片数 > 2 应能区分
3. 让 `send()` 不再记录 → 断言因「没有样本」失败，而不是恒真通过

第 3 条尤其重要：**样本为空时必须显式失败**，不能因为 `every()` 对空数组恒真而假绿。

## 保留的墙钟断言

「快的那台整体显著快于慢的」这条**不保留** —— 它正是翻车的那条。改为服务端时刻后，
「两列耗时不同」（对比功能的真实需求）由 e2e 断言，而不是靠这条单测。
