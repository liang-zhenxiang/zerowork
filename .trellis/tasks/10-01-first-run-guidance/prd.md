# 首次运行指引：让用户知道未签名应用怎么打开

## 用户的原话

> 「我刚下载了这两个包，为什么有 1 个安装之后打不开呢？**是正常的吗？**」
> （arm64 的 dmg 打不开；x64 的能开但「提示使用什么隐私之类的」）

## 已核实的事实（不是猜）

| 检查 | 结果 |
| --- | --- |
| dmg 校验和 | `hdiutil verify` → **VALID**，文件完整 |
| 内部二进制架构 | **arm64**（与用户的 M4 一致） |
| `Info.plist` | 标识与版本都正确 |
| 直接运行二进制 | **能起来** —— daemon 启动、IPC 应答 |
| 代码签名 | `flags=0x20002(adhoc, linker-signed)` —— **未签名** |

**结论：是 macOS 的 Gatekeeper 拦截，不是包坏了。** 用户问「是正常的吗」——
说明我们在**他此刻会看的地方**没有告诉他这件事。

## 为什么这是产品问题，不是「用户不会用」

1. **README 只在角落写了「右键 → 打开」**，而用户的第一反应是「是不是坏了」
2. **两个架构的包表现不同**（一个右键放行过、一个没有），用户会以为是包的问题
3. **macOS 的提示文案本身不告诉用户该做什么**
4. **用户是从 Release 页下载的** —— 那里才是他此刻在看的界面，
   而指引只在仓库文档里

## Requirements

- R1 **把首次运行的指引放到三个地方**，且都要**显著**：
  - `README.md` / `README.en.md` 的「安装 / 下载」一节
  - `docs/USAGE.md` 的开头（不是角落）
  - **`release.yml` 生成的发布说明** —— 这是最重要的一处，
    因为用户此刻就在这个页面上。**确认它足够靠前、足够显眼**
- R2 **两个平台都要写**：macOS（右键打开 / 系统设置里放行）与
  Windows（SmartScreen 的「仍要运行」）
- R3 **查清 `codesign` 的 `Identifier=Electron`**：`Info.plist` 里是正确的
  `io.github.liang-zhenxiang.zerowork`，但签名报的标识是 `Electron`。
  查这是否影响 Gatekeeper 判定、能否修（`electron-builder.yml` 的签名配置）
- R4 **评估签名/公证的成本与收益**，给出结论。若决定不做，
  把「未签名」这件事在**下载页明确说清**
- R5 **用测试钉住**：`release.yml` 生成的发布说明里**必须包含首次运行指引** ——
  防止某次改版把它删掉

## Acceptance Criteria

- [ ] 三处都有指引，且都不是「角落里的一句话」
- [ ] 发布说明里指引出现在**靠前**的位置（在 PR 清单之前）
- [ ] R3 有明确结论（能修就修，不能修说明为什么）
- [ ] R4 有明确结论与依据
- [ ] 新增的检查能**在指引被删掉时失败**（反向验证）
- [ ] `npm run lint:all` 全过

## 约束

- **不做自签名脚本、不教用户绕过 Gatekeeper** —— 那是在教用户绕过系统安全机制，
  且会让「未签名」这件事显得可以糊弄过去
- 改动以**文档与工作流**为主，尽量不动应用代码
- 不改 `release.yml` 里已经正确的部分（PR 清单的中文化刚做完）

## 难度

小到中。主要是**文案落点**与**验证 Release 页**。
