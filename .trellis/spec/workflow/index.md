# 开发流程规范：调度者与验收者

> **本页规定「谁来做、谁来看」**。它约束的是 AI 助手的工作方式，不是代码风格。
> 每个任务开始前读一遍。

---

## 一、角色分工（硬规则）

| 角色 | 谁 | 做什么 |
| --- | --- | --- |
| **调度者** | 主会话 | 拆解任务、准备上下文、派发子 agent、控制节奏 |
| **实现者** | **子 agent** | 真正写代码、改文件、跑测试 |
| **验收者** | 主会话 | 独立复核产物、做反向验证、判断能否合并 |

**主会话不直接下场写功能代码。** 功能的实现一律由子 agent 完成。

这条不是形式主义，有三个实际理由：

1. **验收的独立性**。自己写自己验有盲区 —— 你会不自觉地按自己的实现思路去验，
   恰好绕开自己没想到的边界。分开之后，「写下它的人」与「挑它毛病的人」
   不是同一个，这才能发现真正的缺陷
2. **上下文的效率**。子 agent 在自己的上下文里读大文件、试错、重跑，
   这些噪音不进入主会话。主会话保持清醒，才能持续做判断
3. **并行**。互不依赖的工作可以同时推进，而单线程的主会话做不到

> ⚠️ **例外只有一类**：主会话可以直接改**流程与规范本身**
> （`AGENTS.md`、`.trellis/spec/**`、`.trellis/workflow.md`、脚本与工作流）。
> 那些是「调度者的工具」，自己维护更省事。**功能代码不在此列。**

## 二、派发子 agent 的要求

派得不好，子 agent 会产出看起来对、实际错的东西。派发时必须给全：

### 必给的四样

1. **工作目录与分支**，以及「**不要切分支、不要 commit**」这类边界。
   不写清楚，它可能自己提交，打乱 PR 粒度
2. **参照样板**：让它先读一个**已经做好的例子**，照着写。
   比空口描述风格有效得多
3. **明确的硬要求**，尤其是否定型约束：
   - 「不要削弱任何既有断言」
   - 「不改 `resources/**`」
   - 「不引入运行时依赖」
   - 「遇到不支持的输入要明确报错，不要返回一个看似正常的结果」
4. **验收标准**：什么算完成、要回报什么证据

### 要求回报证据，不要只看结论

**「已完成」「全部通过」不是证据。** 要求它回报：

- 具体的数字（断言条数迁移前后对比、通过 X/Y、耗时变化）
- **它怎么验证的**（跑了什么命令、看到什么输出）
- **遇到了什么问题**、它的判断依据是什么
- **有没有发现原本被掩盖的问题**

> 实战价值：本项目 e2e 迁移时，子 agent 报回了
> 「`app.requestSingleInstanceLock()` 落在 userData 目录、与
> `ZEROWORK_CONFIG_DIR` 无关，所以 e2e 不能并行跑」——
> 那是一个**极像随机 flake** 的真 bug，靠主会话自己逐个跑是发现不了的。

### 允许并鼓励它报告「任务描述与现状不符」

派发时的假设可能是错的。明确告诉它：**发现前提不成立就说，不要硬做。**
本项目的真实例子：一次派发时仓库停在错误的分支上，子 agent 没有硬着头皮做，
而是回报了差异 —— 那比默默产出一堆错位置的文件好得多。

## 三、验收者的职责

子 agent 说完成，**不等于**完成。验收至少要过这几关：

### 1. 独立复核，不轻信报告

- 自己看 `git diff`，**逐条核对被删的行** —— 尤其要确认「没有削弱断言」
- 报告说「等价替换」时，检查新的失败信息**是否真的不弱于原来**
- 数字要对得上：它说迁移前 22 条后 40 条，就抽查几个

### 2. 反向验证（本项目最看重的一条）

**没有反向验证的测试防线是假的。**

- 测代码 → 注入缺陷，确认**恰好**相关的用例变红、其余不受影响
- 修 bug → 复原成修复前的状态，确认症状**确实**复现
- 改行为 → 确认旧行为确实不再发生

> 本项目已做过的真实反向验证（可作范例）：
> - 破坏 PNG 解码器的 Paeth 还原 → **恰好**「滤波类型 4」变红，其余 18 条不受影响
> - 去掉 e2e 的 userData 隔离 → 并行跑时 `dialog-native` 退出码 1；加回去双双通过

### 3. 自己再跑一遍关键命令

至少 `npm run lint:all`，以及被改动领域的核心测试。
不看它跑，看**你**跑。

### 4. 判断「这个改动该不该做」

子 agent 会照你说的做，**不会替你判断这件事该不该做**。
验收时要回头问：

- 这个改动是否有**已记录的刻意决定**与之冲突？
- 它有没有碰不该碰的文件（`resources/**`、大块 chunk 文件）？

> ⚠️ 真实教训：某次审计把 CSS 里 4px/5px 的微圆角判为「不统一、要收敛」，
> 但 `app.css` 里**明确记录着一次 158 处 `border-radius` 的全量审计**，
> 结论就是「4/5px 保留不归档」。差点改掉一个有据可依的刻意决定。
>
> **教训**：判定「这是问题」之前，先在代码里搜有没有关于它的决策记录。
> 本项目习惯把刻意偏离写进注释 —— 看到「保留」「例外」「登记」这类字样要停下来读。

## 四、反面模式（不要这样做）

| 反面模式 | 为什么不行 |
| --- | --- |
| 主会话直接写功能代码 | 失去验收独立性；噪声灌进主上下文 |
| 派发时只说目标，不说约束 | 它会用「最省事」的方式做，往往就是错的那种 |
| 同时改多个不相干的模块 | 出问题时无法归因，回滚代价大 |
| 子 agent 报了「遇到问题」就重派一个 | 先读它的判断 —— 那往往是最有价值的信息 |
| 拿「已完成」当验收通过 | 报告不是证据，产物才是 |
| 为了并行而把有依赖的任务拆开 | 依赖写进任务产物，不要靠调度顺序隐式表达 |

---

## 五、与 Trellis 任务流程的关系

- **一个任务 = 一个分支 = 一个 PR**
- 子 agent 的产出落在当前分支的工作区，**由调度者统一提交** ——
  不要让多个子 agent 各自 commit
- 任务产物（`prd.md` / `design.md` / `implement.md`）由**调度者**维护：
  它掌握全局，子 agent 只有局部视角
