# daemon（Agent 内核）编码规范

> `src/main/daemon/` —— 40 个模块、约 19,500 行。**改这里之前先读完本页。**

---

## 这一层是什么

内嵌的 Agent 内核，跑在**独立的 `utilityProcess`** 里（`src/main/index.js` 用
`utilityProcess.fork` 拉起）。它持有会话生命周期、模型凭据、MCP 连接、自动化调度、
沙箱调度、资源加载、审计与账本。

**为什么是独立进程**：它要 `await import` 整个 pi SDK，初始化慢；且作为执行**不可信内容**
的组件有崩溃风险。隔离后崩了不带走界面，慢启动不卡窗口。

---

## 动手前的检查清单

- [ ] **改动是否触碰模块顶层求值？**（见下「初始化顺序」）—— 这是本层最高频的真实事故
- [ ] **新增/修改的 IPC 处理**，是否在 `src/shared/ipc.js` 里登记了通道常量？
- [ ] **是否引入了新的跨模块顶层引用**？用 `npm run check:daemon-graph` 验证
- [ ] **权限相关的改动**是否仍满足「宁可拒绝，也不静默降级」？
- [ ] **是否落盘在先、推送在后**？（界面上看到 ⇒ 记录已写下，这个顺序是契约）
- [ ] 改完跑 `npm test`（单测）+ 相关的 `tests/e2e/` 用例

## 一、初始化顺序：本层最容易踩的坑

40 个模块的**顶层求值顺序由 import 图决定**。在顶层引入新的跨模块引用，
可能触发 TDZ 错误：

```
ReferenceError: Cannot access 'x' before initialization
```

这个错误**只在真实启动时出现**，静态检查看不出来。所以：

- 顶层**只做声明**，跨模块的**使用**放进函数体（延迟到调用时求值）
- 确有顶层互相引用的必要时，用 `npm run check:daemon-graph` 检查图是否成环
- 改动 daemon 的 import 结构后，**必须真实启动一次应用**验证，不要只看测试绿

## 二、权限与沙箱：两条独立的防线

| 防线 | 位置 | 作用 |
| --- | --- | --- |
| 权限判定 | `permission-rules.js` | 命令与路径是否需要用户确认 |
| 沙箱模式 | `SANDBOX_MODES` + `sandbox/` | 命令在何种隔离环境执行 |

**关键性质：权限判定在 daemon 侧、独立于模型。** 模型无法通过「说这是安全的」绕过它。
任何把权限判定下放到提示词、或让模型可以自证的改动，都要拒绝。

### 宁可拒绝，也不静默降级

沙箱能力在启动时探测（`probeSandbox`），失败会被分类（`classifyFailure`）。
**受限档在沙箱不可用时直接拒绝执行命令**，而不是「无约束地跑一下」。

> 这是本项目已确立的设计原则。用户以为有约束、实际没有，比直接报错更危险。
> 任何「为了让功能看起来能用而放宽安全约束」的改动都要拒绝。

平台差异是**有意为之**：命令沙箱靠 `koffi` 调 Windows 专有的 `kernel32` / `advapi32`，
macOS / Linux 上受限档直接拒绝执行 —— 这也是本项目不发 Linux 安装包的原因。

## 三、数据流与顺序契约

一轮消息在 daemon 内的路径（完整版见 `docs/ARCHITECTURE.md`）：

```
会话构造 → 模型凭据 → MCP 连接 → 资源加载 → 提示词组装
  → session-host.js  核心运行循环
  → session-state.js 状态归约
  → session-view.js  投影成时间线 / diff / 文件呈现
  → session-files.js 落盘
  → push 事件到渲染层
```

两条由此而来的**契约**：

1. **界面渲染的数据是「投影」，不是 daemon 原始状态。** `session-view.js` 决定
   「什么值得显示」。那一层出错的表现是「数据区空白或停在加载态」而**不是崩溃** ——
   这类问题只有真正调一次 IPC 才能发现（这就是 e2e 里「IPC 功能性」那层存在的理由）
2. **落盘先于界面更新。** 所以「界面上看到了」意味着「记录已经写下了」。
   不要为了「让界面先响应」把顺序倒过来

## 四、审计与可观测

审计日志记录四类事件：`command`、`sandbox`、`runtime`、`audit`。

**反直觉但刻意的行为要保留并写进测试**：

- 清空审计日志会**留一条 `audit/cleared`** —— 清空本身也是被审计的事件
- 移除工作区**不删磁盘目录** —— 移除的是注册关系，不是数据
- 查询不存在的路径返回 `{kind:"missing"}` 而不是抛错

---

## 五、错误处理

**错误要可诊断**：给出原因与逃生指引，而不是一句「操作失败」。

- 报错信息里带上**足够定位的上下文**（哪个模块、哪个路径、哪个阶段）
- 分类失败（如 `classifyFailure`）时保留**原始错误**，不要只留分类结果
- 面向用户的错误要说明「下一步能做什么」

## 六、禁止事项

- **不为了 lint 通过而大规模重排本目录**。这里是大文件，
  重排会产生淹没真实改动的巨型 diff（见 `AGENTS.md` 红线 6）
- **不删除 `$1` `$2` 这类变量名后缀** —— 那是构建工具消解命名冲突的结果（红线 7）
- **不在日志中输出凭据或内网地址**（红线 8）
