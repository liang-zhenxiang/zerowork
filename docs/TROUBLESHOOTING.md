## 启动与界面

### 卡在「正在启动」，界面一直不出来

**现象**：窗口开了，样式正常，但内容区永远停在「正在启动」，等多久都不动。

**原因**：已知竞态。daemon 是独立进程（`utilityProcess`），它启动完成后会**推送**一条
ready 状态给渲染层；而渲染层同时也在**注册监听器**。两者谁先完成取决于机器 ——
如果推送早于监听器注册，那条消息就永久丢失了，而界面只会一直等它。

**解决**：正常情况下你不需要做任何事 —— 应用为消除这个竞态留了一条主动查询通道
（`INVOKE.daemonStatus`），渲染进程挂载后会主动查一次。如果你**确实**卡在这里，说明
还有一条没覆盖到的路径，请按 [SUPPORT.md](../SUPPORT.md) 提 Issue，并附上
「诊断」页面里 daemon 的状态与主进程日志。

**不该用这个方案的情况**：如果你配置了自定义 `ZEROWORK_RESOURCES_DIR` 且指向了
错误的目录，表现也是「起不来」，但原因完全不同 —— 先在「诊断」里确认资源目录是否被正确读到。

### 点开 xlsx / 代码 / JSON 预览，整个面板变成「界面渲染出错」

**现象**：在工作空间里点开一个 `.xlsx`（或 `.js` / `.json`），整个面板变成
「界面渲染出错」，要点重新加载才能恢复。

**原因**：渲染层的懒加载块用**字面量字符串**声明自己的依赖表
（`m.f||(m.f=["./office-xlsx.js", "./office-xlsx.css", ...])`），这些字符串是运行时拼成
URL 去预加载的，构建工具不会改写它们。所以**一旦产物文件名带上内容哈希**，
表里每一项就都指向不存在的文件；其中 CSS 那几条是致命的 —— 预加载助手对 CSS 加载失败会
reject 懒加载 promise，未拦截的 `vite:preloadError` 直接抛出去，`<Suspense>` 兜不住。

**解决**：升级到 `0.2.0` 或更高版本。这个问题在 `0.1.4-zerowork.23` 中已修复
（产物改用无哈希的语义名，并给每个 chunk 补回它自己的样式表 import）。

**不该用这个方案的情况**：如果你是**自己构建**的，且改过 `electron.vite.config.mjs`
的 renderer 段 —— 那升级帮不了你，请把产物命名改回语义名，并跑
`npm run check:renderer-assets` 确认契约成立。

## 安装包被系统拦下

### macOS：双击提示「已损坏，无法打开」或「无法验证开发者」

**现象**：

```
“ZeroWork”已损坏，无法打开。你应该将它移到废纸篓。
```

（Apple Silicon 上常见这个措辞；Intel 机器上可能是「无法验证开发者」。）

**原因**：安装包**没有代码签名，也没有经过 Apple 公证**。macOS 对未签名的下载产物会
加上隔离属性，Gatekeeper 于是拒绝直接启动。「已损坏」这个措辞是误导性的 ——
文件本身完好，只是签名缺失。

**解决**（任选一种）：

1. 右键点应用图标 → **打开** → 在弹窗里再点 **打开**（只需一次，之后正常双击）
2. 系统设置 → **隐私与安全性** → 拉到底部 → 找到被拦截的提示 → **仍要打开**
3. 命令行去掉隔离属性：

   ```bash
   xattr -dr com.apple.quarantine /Applications/ZeroWork.app
   ```

**什么情况下不该用这个方案**：**永远不要**对来源不明的安装包做第 3 步。
这一条的前提是「你确认这个包来自本项目的 Releases 页面」。
去掉隔离属性等于放弃系统对未知来源的最后一道检查。

**为什么不去签名**：代码签名需要付费的开发者证书。
在没有证书的情况下，CI 能做到的天花板是 ad-hoc 签名（能把「已损坏」降级为
「无法验证开发者」），公证则完全做不到。维护者拿到证书后会在发布流程里补上。

### Windows：SmartScreen 提示「Windows 已保护你的电脑」

**现象**：运行安装包时出现蓝色提示，按钮只有「删除」和「不运行」，
要点小小的「更多信息」才看得到「仍要运行」。

**原因**：同上 —— 没有代码签名证书，安装包的发布者不是「已知发布者」。

**解决**：点 **更多信息** → **仍要运行**。

**什么情况下不该用这个方案**：同上，只对你确认来源的包这么做。

## 命令执行

### macOS / Linux：命令被拒绝执行

**现象**：Agent 想跑一条命令，界面报「为避免在没有操作系统写入约束的情况下执行命令」
之类的理由并给出逃生指引，命令没有执行。

**原因**：**这是有意的设计，不是缺陷。** 命令沙箱靠 `koffi` 调 Windows 的
`kernel32` / `advapi32`，是 **Windows 专有**的。在 macOS / Linux 上
`sandbox.probe()` 必然返回 `available: false`：

| 权限档 | 行为 |
| --- | --- |
| `read-only` / `workspace-write`（**含默认档**） | 命令被**直接拒绝** |
| `danger-full-access` | 可以执行（不经沙箱、直接 spawn） |

**解决**：见下。

**什么情况下不该用这个方案**：**不要把默认权限档改成「完全访问」当作常规做法。**
「完全访问」意味着命令不经任何约束直接跑在你的机器上，而命令内容来自模型 ——
而模型的上下文里可能混入不可信内容（你打开的文件、抓取的网页、MCP server 的返回）。
正确的做法分两种：

- **只需要偶尔跑命令**：临时切到完全访问，跑完切回来
- **需要长期在 macOS / Linux 上用命令执行**：为本平台实现一个等价的沙箱后端
  （`src/main/sandbox/`），或把操作放在 Windows 上做

### 界面显示「bash 运行时：未安装」，但点了安装没反应

**现象**：在 macOS 上看到 bash 运行时未安装的提示。

**原因**：这**曾经是一个界面误导问题**（已修）。Bash 运行时是 Windows 专有的产物
（PortableGit 的 `.7z.exe`），macOS / Linux 自带 bash、不需要托管。
早期版本不过滤平台，于是界面在 macOS 上显示「bash 运行时：未安装」并给出安装按钮，
用户点下去会下载一个跑不起来的 Windows 可执行文件。

**解决**：升级到 `0.2.0` 或更高版本，非 Windows 平台上 Bash 运行时不会再出现在清单里。

**什么情况下不该用这个方案**：如果你是自己构建的且改过 `RUNTIME_PLATFORMS`，
那就要自己检查平台过滤逻辑。

### 运行时未就绪，脚本能不能跑

**现象**：诊断页显示某个托管运行时未安装。

**原因与解决**：**这不阻塞功能。** 托管运行时是**可选加速器**：
`planRuntimeInjection` 对未就绪的运行时给出 `not-ready` 决策并**跳过注入**，
脚本照常用系统 `PATH` 里的工具执行。

**不该用这个方案的情况**：如果你依赖的正好是托管运行时提供的**特定版本**
（比如某个只在该版本里有的行为），那跳过注入就改变不了事实 —— 请显式安装它。

### 报错 `fd is not available and could not be downloaded`

**现象**：模型想找文件时报这条，而且要等大约 10 秒才失败。

**原因**：pi agent harness 的 `find` / `grep` 工具依赖外部二进制 `fd` / `rg`。
它自己的兜底是「本机找不到就从 GitHub 下载」，那条路径在国内网络下经常不通，
而它的版本解析有 10 秒超时 —— 失败原因还被调用路径吞掉了，所以你只看到这一句。

**解决**：应用会随包带上这几个二进制，并在启动时补到 pi 的 bin 目录
（幂等：已就位且可能更新时不会覆盖）。如果你看到这条，说明那次补位没有成功 ——
检查 `resources/bin/` 下的 `fd.exe` / `rg.exe` / `uv.exe` 是否齐全
（**克隆仓库时如果缺这几个文件，多半是 `.gitignore` 把 `*.exe` 吞了**；
仓库里有一道 `npm run check:resources` 专门守这件事）。

**不该用这个方案的情况**：如果你在非 Windows 平台上 —— 随包的这几个二进制
**只有 Windows x64 版**，其他平台本就不参与补位，`fd` / `rg` 需要你自己装。

## 模型连接

### 发消息没有任何反应，或者一直转圈

按顺序查三件事：

1. **「设置 → 模型」里的接入地址与模型名是否填对**。本地端点（Ollama / vLLM 等）
   通常要带 `/v1` 后缀
2. **网络能不能到那个地址**。自建网关常在内网，而开发模式下的 daemon 是另一个进程 ——
   它继承的是**启动应用时的环境变量**，不是你在某个终端里 export 的
3. **Key 是否有效**。鉴权失败有时表现为挂起而不是报错，
   取决于供应商返回的是什么

### 回复是空的，但状态显示成功

**现象**：消息发出去了、状态正常，但回复内容为空。

**原因**：多半是**流式事件类型与预期不符**。不同供应商（以及同一供应商的不同兼容层）
在 SSE 里用的事件名不一样，拼错时不会报错，只是解析出空内容。

**解决**：仓库里有一层端到端测试专门验证协议对接（用真实端点跑一轮对话，
并校验回复里带**真实 token 用量**）。跑它能看到协议层到底哪里对不上：

```bash
npm run test:gui:real
```

它从 `~/.claude/settings.json` 的 `env` 里读 `ANTHROPIC_BASE_URL` /
`ANTHROPIC_AUTH_TOKEN` / `ANTHROPIC_MODEL`，**不打印凭据**；端点不可用时整轮跳过。

**不该用这个方案的情况**：测试用的端点配置与你在应用里配的是两套东西。
测试通了不代表应用里配的那个供应商通了 —— 反之亦然。

## 文档解析

### PDF / DOCX / XLSX 读不出内容

按顺序查：

1. **文件本身是否可读**。「资料库」里先看预览能不能出来 —— 预览能出来说明文件没问题，
   问题在提取链路
2. **DOCX 需要 Python 引擎**。docx 的读写走的是 `resources/docx-engine/` 里的 Python 实现，
   需要可用的 Python 环境。诊断页会显示它的状态
3. **老版 `.doc`（非 docx）不在支持范围**。那是完全不同的二进制格式
4. **扫描件 PDF 没有文本层**。解析出来是空的，因为图上本来就没有文字

**什么情况下不该用这个方案**：如果你要处理的是**扫描件**，正确的方向是 OCR，
而不是继续调解析参数。本项目不做 OCR。

### 解析库的安全提示

项目依赖的文档解析库存在已知漏洞（`decompress` 的 Zip Slip 类问题、`xlsx` 的原型污染与
ReDoS），**都没有在当前版本里修复**。它们正是用来读你打开的文件的。
跟踪与处置见 [依赖安全 Issue](https://github.com/liangyuxiang/zerowork/issues/15)，
威胁模型见 [SECURITY.md](../SECURITY.md)。

在修复之前：**只打开你信任来源的文档**。这是标准的「不要让不受信任的解析输入
进到有漏洞的解析器」原则。

## MCP 连接器

### 连接器状态一直显示「连接中」

**现象**：MCP 连接器的状态一直是 `connecting`，等多久都不会变成 `connected`。

**原因**：这里的 `"connecting"` **不是「正在连」，而是「还没开始连」**。

MCP 客户端是**按会话桶**创建的，真正的连接发生在**会话构造期**。
桶里还没有构造过任何会话时，配置查询拿不到活句柄，只能按配置**合成**一个
`connecting` 占位 —— 而那个占位永远不会自己变成 `connected`。

**解决**：**发一条消息**（在「助理」里随便发一条）。发消息才会构造会话，
构造之后连接才会建立，状态随之更新。

**不该用这个方案的情况**：如果你**已经发过消息**且状态仍是 `connecting`，
那就不是这个原因了 —— 那说明连接真的失败了，请看下一条。

### 连接器真的连不上

排查顺序：

1. **stdio 类型的命令路径对不对**（要用绝对路径，且注意 Windows 与 POSIX 的差异）
2. **环境变量展开了没有**。配置里支持 `${VAR}` 形式的展开，
   但展开的是**应用进程的环境变量**，不是你的 shell 环境
3. **server 自己启动得起来吗**。把配置里的命令手动在终端跑一遍，
   它的 stderr 会告诉你原因

## 自动化任务

### 到点了任务没跑

1. **任务开关是否打开**（关闭的任务不会入队）
2. **时间配置是否合法**（每周任务需要指定星期；间隔任务不能是 0）
3. **应用是否在运行**。定时任务是**应用内**的调度，应用没开就不会触发 ——
   它不是一个常驻后台服务

### 任务跑了但没结果

任务会**起一个新会话**跑提示词，产出留在那个会话里。
到「助理」的会话列表里找它，而不是在自动化页面等一个结果卡片。

## 仍然没解决

按 [SUPPORT.md](../SUPPORT.md) 的分流走：

1. 再搜一遍本页与现有 Issue（关键词用**报错原文**）
2. 使用疑问 → [Discussions](https://github.com/liangyuxiang/zerowork/discussions)
3. 确认是 Bug → [提 Issue](https://github.com/liangyuxiang/zerowork/issues/new/choose)，
   附上报错原文、复现步骤、平台与版本
4. 安全漏洞 → **不要开公开 Issue**，见 [SECURITY.md](../SECURITY.md)
