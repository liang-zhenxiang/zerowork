# ADR-0001：docx 修订的保真写回路径

- **状态**：已决定（v1 支持受限范围，待实现）
- **日期**：2026-11-23
- **关联**：Issue #460（本评估）；#456 / #457 / #458 / #459（修订模式、工作台、写回三道闸、e2e）
- **一句话结论**：**v1 只支持「正文段落里、单个 run 内的整段文字替换」**；跨 run、
  改结构、表格、页眉页脚 / 脚注 / 批注一律**拒绝并说明原因**。不提供 Word 原生
  修订痕迹（`w:ins` / `w:del`），也不声称兼容它。

---

## 一、背景

修订模式目前只覆盖 Markdown / 文本。办公用户的真实待改文档大多是 `.docx`，
所以「为什么 Word 文档不能修订」会反复被问；而反过来，若为了「看起来能用」
就把 docx 当成纯文本处理，用户拿到的是**一份版式被悄悄改掉的文档** ——
这比拒绝更糟。

本 ADR 先回答三个问题，再据此决定 v1 的范围：

1. `.docx` 能不能**保真**写回？保真到什么粒度？
2. 三条候选路径各自会丢什么？
3. 失败时能不能保证**原文件不被破坏**？

### 「修订」在这里指什么

本项目的「修订」是**应用内的建议 → 接受 / 拒绝**流程（#456 / #457 / #458），
不是 Word 的「修订痕迹」。接受一条建议后，文档被**直接修改**；在 Word 里打开
不会看到可以「拒绝」的修订标记。这条边界必须在文档与提示里说清，不能含糊。

### 已确立的三道闸（#458）

任何 docx 写回都必须依次满足，任一步失败都不写目标文件：

1. **哈希守卫**：当前文件 SHA-256 必须等于建议的 `baseSha256`，否则拒绝；
2. **版本先行**：写盘前先存一份旧版本（`version-store`），存不下就中止；
3. **审计不含正文**：只记建议 id、文件名与段数。

---

## 二、三条路径

| 编号 | 路径 | 在应用里的位置 |
| --- | --- | --- |
| ① | **OOXML 包内 run 级修补**：解包 zip，只改 `word/document.xml`（或页眉页脚等部件）里目标 `w:t` 的文本，按原条目顺序重新打包 | 尚未实现；本 ADR 建议作为 v1 写回路径 |
| ② | **python-docx 全量重建**：读原文档，用 `python-docx` 新建一份再写入 | 现仅用于生成（`html_to_docx` 内部），未用于修订 |
| ③ | **docx → 中间标记 → docx**：`docx_to_html` 提取成 HTML，再用 `html_to_docx` 重新生成 | 就是现有的 `docx_extract` / `docx_convert` 两个工具 |

> PRD 把路径 ③ 写作「docx → Markdown → docx」。应用里真实存在的是
> **docx → HTML → docx**（`src/main/daemon/doc-extract.js` 调 `docx_to_html` 与
> `html_to_docx`）。两者是同一类路径（先降维成语义标记、再重新生成），
> 而 HTML 的表达力**强于** Markdown —— HTML 都保不住的东西，Markdown 只会丢得
> 更多。所以实测 HTML 链，并把结论当作这条路径的**上界**。

### 路径 ① 的实验口径（重要）

修补只做「一个 `w:t` 的文本替换」：

- 用 `--find` 的**完整文本**匹配一个 `w:t`，**要求全文件唯一命中**；找不到或
  多处命中一律拒绝；
- 只替换该元素内部的文本字节，保留标签与 `xml:space` 等属性；
- zip 按原条目顺序写出，每个条目沿用原来的时间戳、压缩方式与权限位；
- 先写临时文件，最后一步 `os.replace` 原子替换 —— 过程中任何异常都不会留下
  半成品，也不会动到原文件。

## 三、实验方法

### 夹具

`tests/fixtures/docx-revision/make_fixtures.py` 用 **python3 标准库**生成两个
夹具；生成是**确定性**的（条目顺序、时间戳、XML 内容都固定），任何机器重跑都
得到同样的字节，所以实验可复现。生成产物也提交在同目录（3.6 KB / 4.0 KB），
可直接打开核对；重建后的 SHA-256 应为
`a-styles.docx = 5f0bf49…`、`b-table-header-footer.docx = a3ab4ce…`（完整值以
`shasum -a 256 tests/fixtures/docx-revision/*.docx` 为准）。

| 夹具 | 内容 | 覆盖的保真线 |
| --- | --- | --- |
| `a-styles.docx` | 标题样式、正文字体字号、加粗 run、斜体 run、两个编号列表项、外部超链接、**一段被拆成两个 run 的文字** | 样式 / 编号 / 超链接 / 跨 run |
| `b-table-header-footer.docx` | 表格（表头行、底纹、边框、固定列宽）、页眉文字、带 `PAGE` 域的页脚、页面尺寸与页边距 | 表格 / 页眉页脚 / 域 / 分节 |

夹具 A 共 6 段、10 个 run、1 个超链接、2 个编号段；夹具 B 有 1 个表格（6 个
单元格）、1 个页眉、1 个页脚。两个文件都能被 `python-docx` 正常打开 —— 这是
「没有用 Word 验证」的替代证据（见「已知限制」）。

### 保真清单

`inspect_docx.py` 只用标准库读 OPC zip，输出可 diff 的 JSON：条目顺序与每个
条目的 sha256、样式 / 编号 / 页眉页脚 / 批注 / 脚注部件是否存在、段落与 run、
加粗 / 斜体 / 下划线、超链接及目标、编号段、表格与单元格、页眉页脚文字与
`PAGE` 域、分节 / 页面尺寸 / 页边距、按 body 顺序拼出的纯文本。

### 环境

- macOS（darwin 24.4.0），系统 `python3` 3.14.0（**没有** python-docx）；
- 应用托管 venv `~/.venv-html-to-docx`，Python 3.12.11，`python-docx` 1.2.0，
  `html4docx` / `lxml` / `beautifulsoup4` 可用 —— 实验 B、C 用它真跑；
- 两个引擎直接以 `PYTHONPATH=resources/docx-engine` 调用，**没有启动 Electron**；
- 本机没有 Microsoft Word，所以「Word 能否打开」只能以 `python-docx` 打开、
  XML 解析通过作为代理证据 —— 这一点在结论里如实标出。

## 四、实验结果

所有命令见「七、复现」。以下数字都来自 2026-11-23 的实测输出。

### 4.1 路径 ①：文本替换

| 目标 | 改动的部件 | 改动条目 | 其余条目 | 清单差异 |
| --- | --- | --- | --- | --- |
| A 正文「本季度营收」→「本季度营业收入」 | `word/document.xml` | 1 / 8 | 7 个**逐字节一致** | 仅 `text` |
| B 表格单元格「营业收入」→「营业收入（调整后）」 | `word/document.xml` | 1 / 9 | 8 个逐字节一致 | `table_text`、`text` |
| B 页眉「内部资料 · 仅供评审」→「内部资料（已修订）」 | `word/header1.xml` | 1 / 9 | 8 个逐字节一致 | `headers` |

- 条目顺序、时间戳、压缩方式、权限位全部保留；改后的 XML 仍是合法 XML；
- 修补后的 A 能被 `python-docx` 打开，段落文字为
  `['季度报告', '本季度营业收入 增长 12%，详见 公开报告。', …]`，样式仍为
  `Heading 1 / Normal / List Paragraph`；
- 单次替换的改动面：A 的 `document.xml` 只动了 15 字节（偏移 432），
  新文本 21 字节。

**失败路径**（同一脚本）：

| 场景 | 结果 |
| --- | --- |
| 全文找不到目标文本（如 `--find 不存在的文本`） | 退出码 1，**不产出文件** |
| 目标文本跨两个 run（夹具 A 的「跨 run 的文本」） | 退出码 1，**不产出文件**；原文件不动 |
| 多处命中 | 拒绝（本实验只允许唯一命中） |

跨 run 失败不是脚本的缺陷，而是**真实文档的常态**：Word 会因为拼写检查、
格式变化把一段话拆成多个 run。路径 ① 的 v1 必须把这个限制转成明确拒绝，
不能把「找不到」当成「改成功了」。

**结构编辑**（`experiment_structure.py`，插入 / 删除段落）：

| 操作 | 改动条目 | `document.xml` 字节 | 清单差异 | python-docx 打开 |
| --- | --- | --- | --- | --- |
| 插入一段「补充：数据以审计后版本为准。」 | 仅 `word/document.xml` | 1489 → 1625 | 段落 / run / 样式 / 正文 | 是 |
| 删除「以上数据未经审计。」 | 仅 `word/document.xml` | 1489 → 1364 | 段落 / run / 样式 / 正文 | 是 |

结论：**包级完整性同样成立**（其余条目不变、文件能打开），但代价与文本替换
不是一个量级 —— 实验里用 ElementTree 改结构会把**整个 `document.xml` 重新
序列化**。真实 Word 文档的根元素常带 `mc:Ignorable="w14 wp14"` 与十几个
命名空间声明，朴素重序列化可能丢掉未使用的前缀声明（本夹具只有 `w` / `r`，
不暴露这一点，所以这是**代码审查结论**而不是本实验证据）。生产实现必须做
**定向节点编辑**，并扩展夹具覆盖书签、分节、内容控件后再谈支持。

### 4.2 路径 ②：python-docx

**环回保存**（`Document(path).save()`）：

| 夹具 | 清单差异 | 条目变化 | 逐字节一致的条目 |
| --- | --- | --- | --- |
| A | **无** | 8 → 8 | 1 / 8（只有 `docProps/app.xml`） |
| B | **无** | 9 → 9 | 1 / 9 |

也就是说：python-docx 环回保存**在语义上**没丢这两份夹具的内容，但它会
**重写所有被解析的 XML 部件** —— 7 / 8、8 / 9 个条目逐字节变了。对「保住原
文档」这个目标来说，这已经是一次全包重写；未知部件与扩展是否都能保住，
本实验没有覆盖（见「已知限制」）。

**全量重建**（读取内容后用 `Document()` 新建）：

| 项 | 夹具 A | 夹具 B |
| --- | --- | --- |
| 条目数 | 8 → **17**（新增模板自带 `settings` / `theme` / `customXml` / `thumbnail` 等） | 9 → **19** |
| 样式定义 | 换成 python-docx 默认模板 | 同 |
| 编号 | 2 个编号段 → **0** | — |
| 超链接 | 1 → **0**（退化为纯文字） | — |
| 表格 | — | 底纹 2 → **0**、表头重复标记 1 → **0**、列宽 4675 → **4320**；边框因为重建时套了 `TableGrid` 样式而仍在 |
| 页脚 `PAGE` 域 | — | 有 → **无**（文字变成「第  页」） |
| 页眉 | — | 文字保留，加粗丢失（加粗 run 2 → **0**） |
| 页眉 / 页脚距离 | 851 / 992 → **720 / 720** | 同 |
| 正文文字 | 保留 | 保留 |

结论：全量重建的保真度**取决于你愿意为每种特性重写多少代码**。编号、超链接、
单元格底纹、表头重复、`PAGE` 域、页面细节，每一项都要单独重建；漏一项就是
静默丢一项。这不符合「宁可拒绝，也不静默降级」。

### 4.3 路径 ③：docx → HTML → docx（现有引擎链）

| 项 | 夹具 A | 夹具 B |
| --- | --- | --- |
| 提取 `not_restorable` | 无 | **页码**、**页眉页脚** |
| 提取 warnings | **「超链接按纯文本提取（链接地址未保留）」** | 无 |
| 生成 warnings | 无 | 无 |
| 正文文字 | 保留 | 保留（**多一个空段落**） |
| 标题 | 保留 `h1` | 保留 `h1` |
| 列表 | 2 个编号段保留，但样式 `ListParagraph` → **`ListNumber`**（引擎自己的编号定义） | — |
| 加粗 / 斜体 | 保留 | 保留 |
| 超链接 | 1 → **0** | — |
| 表格结构 | — | 表格、表头 `th`、单元格文字保留 |
| 表格样式 | — | 边框以 6 组单元格边框保留；**底纹 2 → 0**、**表头重复 1 → 0**、列宽 4675 → 4320、表宽 `auto` → **50%** |
| 页眉页脚 | — | **整体丢失** |
| 页面 | 尺寸保留；左右边距 1800 → **1797**、页眉页脚距离 851 / 992 → **720** | 同 |
| 部件 | 换成引擎模板（新增 `settings` / `theme`） | 同 |

结论：这条链**只保证文字和大致层级**。它是一条「按新模板重新排版」的路径，
不是「在原文上改」的路径。用它做修订 = 用户每次接受一条修订，文档版式都被
重排一次 —— 不能接受。

### 4.4 三条路径横向对比

| 维度 | ① run 级修补 | ② python-docx 重建 | ③ HTML 中继 |
| --- | --- | --- | --- |
| 样式定义 | 原样 | 换成默认模板 | 引擎映射，近似 |
| 编号定义 | 原样 | 丢失 | 重建（定义不同） |
| 超链接 | 原样 | 丢失 | 提取端即丢失 |
| 表格结构 | 原样 | 重建（文字 / 网格） | 重建（文字 / 表头） |
| 表格样式 | 原样 | 部分（依赖样式名） | 部分（逐格边框，其余丢） |
| 页眉页脚 / 页码 | 原样（可单独修补） | 文字可复制，域丢失 | 丢失 |
| 批注 / 脚注 / 自定义 XML / 宏 | 原样（不去碰） | 部分保留，全包重写 | 丢失 / 不保证 |
| 改动面 | 单部件、最小字节 | 全包重写 | 全包重生成 |
| 失败能否拒绝且不动原文件 | **能** | 不能（重建已发生） | 不能（重生成已发生） |
| 用于 v1 修订写回 | **是（限文本替换）** | 否 | 否 |

## 五、决策

### 5.1 v1 支持的范围

**支持**：对 `.docx` 的**正文段落**做**文字替换**，且满足全部条件：

- 被替换的整段文字完整落在**同一个 `w:t`** 内（不改 run 边界）；
- 建议里的原文与目标 `w:t` 的文本**逐字**匹配（不做模糊 / 相似度匹配）；
- 该文本在目标部件里**唯一命中**；
- 目标文件是有效 `.docx`（zip + `[Content_Types].xml` + `word/document.xml`）；
- 哈希守卫通过（文件自建议生成后未被改动）。

**不支持（明确拒绝，不降级）**：

| 情况 | 用户看到的提示 |
| --- | --- |
| 文字跨多个 run | 「这段文字在 Word 中被拆成了多段格式，v1 暂不支持直接写回。请在 Word 中手动修改这一处。」 |
| 插入 / 删除段落、改表格、改列表结构 | 「这条修订会改变文档结构（段落 / 表格 / 列表），v1 暂不支持写回。请在 Word 中手动修改。」 |
| 页眉页脚 / 脚注 / 尾注 / 批注里的文字 | 「该修订位于页眉页脚 / 脚注 / 批注，v1 暂不支持写回。」 |
| 域（`w:fldSimple` / `w:instrText`，如页码、目录）里的文字 | 「该修订落在 Word 域里，v1 暂不支持写回。请在 Word 中手动修改。」 |
| 原文已变化（哈希不符） | 「原文已变化，请重新生成修订建议。」（与 #458 一致） |
| 文件被 Word 占用 / 无法原子替换 | 「无法写入：文件可能正被其它程序打开。关闭后重试。」 |
| 老格式 `.doc`、加密文档 | 沿用现有读取链的提示：先另存为 `.docx` / 解除加密 |

### 5.2 必须同时满足的写回顺序

1. 哈希守卫（`baseSha256`）→ 2. 目标文本唯一命中（否则拒绝）→ 3. 版本先行
   （`version-store` 存不下就中止）→ 4. 写临时文件并 `os.replace` 原子替换 →
   5. 写后自检（重新打开 zip、解析 XML、确认目标文本已变、其余条目未变；失败
   则用第 3 步的版本恢复）→ 6. 审计（只记建议 id / 文件名 / 段数，不含正文）。

**同一条建议里的多个 hunk：逐个定位；任一 hunk 定位失败，整条拒绝，不部分
写回** —— 部分写回会让「界面上显示已接受、实际只改了一半」成为可能。

### 5.3 不声称的东西

- **不声称兼容 Word 原生修订格式**：写回后 Word 里没有 `w:ins` / `w:del`
  痕迹，没有「接受 / 拒绝」按钮。这是产品语义，不是实现缺陷。
- **不声称「原文件逐字节不变」**：重新打包会改变 zip 容器本身的字节，保证的是
  「除目标部件外，每个条目的内容字节不变」。哈希守卫与版本库针对的是**内容**，
  不是最终文件的哈希。
- **不声称支持所有 docx**：两条夹具只覆盖样式 / 编号 / 超链接 / 表格 /
  页眉页脚 / 域 / 分节；批注、脚注、图表、SmartArt、内容控件、宏（`.docm`）
  未验证。

## 六、否决的方案

| 方案 | 否决理由 |
| --- | --- |
| 用路径 ②（python-docx 全量重建）做 v1 | 编号、超链接、底纹、表头重复、`PAGE` 域逐项丢失；条目 8 → 17、9 → 19，等于换了一份文档。要保真就得为每种特性重写一遍，成本与风险都不可控 |
| 用路径 ③（HTML 中继）做 v1 | 只保文字与大致层级；超链接在提取端就丢，页眉页脚整体丢，表格底纹 / 表头 / 列宽 / 表宽全变。每接受一条修订就重排一次文档 |
| 「找不到目标文本就整段替换 / 按段落模糊匹配」 | 会悄悄改掉 run 级格式（加粗、字号、颜色），正是本项目反对的静默降级。找不到就拒绝 |
| v1 直接写 Word 原生修订痕迹（`w:ins` / `w:del`） | 与产品内的「接受 / 拒绝」模型冲突（两套待审状态），且需要用户级作者信息、时间戳与复杂的嵌套规则。留作独立研究，不在 v1 |
| 用 ElementTree 朴素重序列化做所有写回 | 文本替换根本不需要重写整个部件；结构编辑则可能丢掉 `mc:Ignorable` 前缀声明。生产实现必须定向编辑节点 |
| 对 `.docm` / 加密文档「尽力一试」 | 宏与加密是安全敏感面，直接拒绝并给出逃生指引 |

## 七、复现

```bash
# 0) 准备
WORK=/tmp/zw-docx-revision
VENV=~/.venv-html-to-docx/bin/python        # Windows：%USERPROFILE%\.venv-html-to-docx\Scripts\python.exe
rm -rf "$WORK" && mkdir -p "$WORK"

# 1) 夹具（stdlib；确定性，重跑字节一致）
python3 tests/fixtures/docx-revision/make_fixtures.py --out "$WORK"
```

## 八、后续拆分（建议，未实际建 Issue）

1. **跨 run 文本替换**：同 `rPr` 的相邻 run 合并后替换；格式不同则拒绝。
   夹具已包含跨 run 段落（`a-styles.docx`）。
2. **结构编辑**：插入 / 删除段落、编辑表格单元格内容。前提是改为**定向节点
   编辑**，并补齐书签、分节、内容控件、批注的夹具与回归测试。
3. **页眉页脚 / 脚注 / 批注文字**：按部件路由修补（实验已验证页眉部件可行）。
4. **真实文档样本集**：批注、脚注、图表、`customXml`、`.docm`、加密文档；
   并补一份需要真实 Word 的人工验收清单（本机与 CI 都没有 Word）。
5. **Word 原生修订痕迹**（可选研究）：若要和 Word 的修订模型共存，需要单独
   的 ADR，不并入本决策。

## 九、已知限制

- **没有用 Microsoft Word 验证**：本机无 Word，只有 `python-docx` 打开与 XML
  解析作为代理。最终「Word 里看起来对不对」仍需人工验收。
- 夹具是手工构造的最小样本，不是真实世界文档；样式继承、主题色、复杂编号、
  内容控件等未覆盖。
- python-docx 环回保存只证明了**这两份夹具**语义无损；未知部件与扩展是否
  总能保住没有验证，因此它仍不适合作为写回路径。
- 路径 ③ 的结论以 HTML 链为上界；Markdown 中继只会更差，未单独实测。
- 结构编辑实验用的是 ElementTree 朴素重序列化，**不是**建议的生产实现。
